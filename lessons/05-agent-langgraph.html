    Agent 與工作流

    這一課結束時，你會有一個多步驟的異常交易處理流程，而且遇到退款這種高風險動作會停下來等人核准——關掉程式、明天再開，還能從原本停住的地方繼續。

    預估時間 10–12 小時 前置 第 2、3、4 課 產出 Agent v1 + 流程圖 新東西 LangGraph

    0這一課要做到什麼

    第 2 課的手寫迴圈能跑，但它有三個限制，而這三個限制正好就是這一課要解決的：

    限制具體問題
    無法暫停要人工核准退款時，程式只能卡在 input() 等著。使用者關掉視窗，整個流程就沒了
    無法恢復跑到一半當掉，重跑就要從頭開始，前面花的錢全部重付
    流程藏在控制流裡「什麼情況走哪條路」散落在 if 和 while 之間，看程式碼看不出全貌，也畫不出流程圖給別人看

    要做的流程長這樣：

    本週產出

    1. Agent v1——畢業專題的主體。前四週的東西（工具、RAG、評估）都接進來。
    2. 一張流程圖——LangGraph 可以自己產生，但你要看得懂、講得出每個節點為什麼在那裡。
    3. 手寫迴圈 vs LangGraph 的優缺點筆記——面試一定會問的題目。

    1先問：這個東西真的需要 agent 嗎

    能寫死的步驟就寫死

    這是本課最重要的一句話，也是最容易被忽略的。每多一個「讓模型自己決定」的環節，就多一個不確定性來源——更難測、更難 debug、成本更高、而且失敗模式更難預測。

    「我做了一個 agent」聽起來比「我做了一個工作流」厲害，但在面試時，能說出「這幾步我刻意寫死，因為⋯⋯」的人，比什麼都交給模型決定的人更有說服力。

    四個判準

    決定某個環節要不要交給模型自主決定時，四個都要是「yes」：

    判準問題這個專案的答案
    複雜度任務是多步驟、而且無法事先完整規定嗎？「要查交易還是查文件還是兩個都查」確實要看問題內容 → yes
    價值結果值得更高的成本與延遲嗎？客服一次查詢省下的時間 → yes
    可行性模型真的做得到這件事嗎？工具呼叫與文件問答都在能力範圍內 → yes
    錯誤成本錯了能被發現並補救嗎？回覆草稿有人看過才送出 → yes
    但退款不行 → 所以退款要人工核准

    第四個判準直接推導出本週的設計

    注意「錯誤成本」那一列怎麼分岔的：擬回覆可以交給模型，因為錯了有人會發現；執行退款不行，因為錢出去就回不來了。

    所以設計上不是「這整個流程要不要用 agent」，而是逐個動作判斷。一個動作越難回復，就越該從「模型自主」移到「固定流程 + 人工關卡」。這個判準在第 7 週加金額上限和稽核日誌時會再用一次。

    固定工作流 ↔ 自主 agent 是一個光譜

    固定工作流 ←─────────────────────────────────────→ 自主 agent
每一步都寫死                                    模型決定所有步驟

  ├─ 可靠、可測、便宜                      ├─ 彈性、能處理沒想到的情況
  ├─ 不會處理意料外的輸入                  ├─ 難測、難 debug、貴
  └─ 流程圖畫得出來                        └─ 每次執行路徑都不一樣

              你的專案應該落在這裡 ↓
              ─────────────●─────────────
              骨架固定、個別節點內部讓模型決定

    本週的設計就是這個混合型：節點之間的流程是你寫死的（固定工作流），但每個節點內部用模型做判斷（局部自主）。LangGraph 正好為這種形狀設計。

    2LangGraph 的核心概念

    uv add langgraph langgraph-checkpoint-sqlite

    LangGraph 只有四個概念要懂：State、Node、Edge、Checkpointer。

    State：在節點之間傳遞的資料

    State 定義 · 點標記看說明
    from operator import add
from typing import Annotated, Literal
from typing_extensions import TypedDict


class AgentState(TypedDict):
    question: str
    intent: Literal["transaction", "docs", "both", "refund", "other"]
    order_id: str | None
    transaction: dict | None
    doc_hits: list[dict]
    draft_reply: str
    needs_refund: bool
    refund_approved: bool | None
    trace: Annotated[list[str], add]
    1
    TypedDict 是「有固定欄位的 dict」。執行時它就是個普通 dict（state["question"] 這樣取值），但型別檢查工具和你的編輯器知道有哪些欄位、各是什麼型別。
    2
    一般欄位的規則是「後寫的覆蓋先寫的」。節點回傳 {"question": "x"} 就把這欄換成 "x"。
    3
    Literal[...] 限制只能是這幾個值之一。這和第 1 課 Pydantic 的 Enum 是同一個思路——把可能的值收斂到有限集合，下游才能放心用 if 比對。
    4
    dict | None：還沒查到時是 None。LangGraph 不會幫你初始化欄位，所以每個可能還沒被賦值的欄位都要能接受 None。
    5
    Annotated[list[str], add] 是 reducer——這一欄的更新規則不是「覆蓋」而是「用 add 合併」。對 list 來說 add 就是串接。

    Reducer 是 LangGraph 最容易誤解的地方

    沒有 reducer 的欄位：節點回傳 {"trace": ["查了交易"]} → 整欄被換成 ["查了交易"]，之前的紀錄消失。

    有 add reducer 的欄位：同樣的回傳 → 附加到既有的 list 後面，變成 ["判斷意圖", "查了交易"]。

    所以「累積型」的欄位（對話訊息、執行軌跡、檢索結果）都需要 reducer，而且這是「節點只需要回傳它改動的部分」這個設計的關鍵——節點不用知道前面累積了什麼。

    處理對話訊息有現成的：from langgraph.graph.message import add_messages，或直接繼承 MessagesState。

    Node：一個函式，吃 state 回傳 state 的一部分

    def lookup_transaction(state: AgentState) -> dict:
    """查交易節點。只回傳它改動的欄位。"""
    order_id = state["order_id"]
    if not order_id:
        return {"transaction": None, "trace": ["查交易：沒有訂單號，略過"]}

    raw = get_transaction(order_id)       # 第 2 課寫的工具
    data = json.loads(raw)
    return {
        "transaction": data if data.get("found") else None,
        "trace": [f"查交易：{order_id} → {'找到' if data.get('found') else '查無'}"],
    }

    節點回傳的是「要更新的部分」，不是整個 state

    新手最常見的錯誤是回傳整個 state（return state）或是手動合併。不需要——回傳一個只含改動欄位的 dict，LangGraph 會依每一欄的規則（覆蓋或 reducer）自己合併。

    回傳整個 state 也能動，但你會失去 reducer 的語意，而且容易不小心把別的節點剛寫入的東西蓋掉。

    Edge：節點之間怎麼走

    from langgraph.graph import StateGraph, START, END

builder = StateGraph(AgentState)

builder.add_node("classify", classify_intent)
builder.add_node("lookup_tx", lookup_transaction)
builder.add_node("search_docs", search_documents)
builder.add_node("draft", draft_reply)
builder.add_node("approval", request_approval)

# 固定邊：一定會走
builder.add_edge(START, "classify")
builder.add_edge("lookup_tx", "draft")
builder.add_edge("search_docs", "draft")
builder.add_edge("approval", END)


# 條件邊：由一個函式決定去哪
def route_after_classify(state: AgentState) -> str:
    intent = state["intent"]
    if intent in ("transaction", "refund"):
        return "lookup_tx"
    if intent == "docs":
        return "search_docs"
    if intent == "both":
        return "lookup_tx"
    return "draft"                    # other：直接讓模型回應


builder.add_conditional_edges("classify", route_after_classify)


def route_after_draft(state: AgentState) -> str:
    return "approval" if state["needs_refund"] else END


builder.add_conditional_edges("draft", route_after_draft)

    START 和 END 是特殊常數

    從 langgraph.graph import。START 是圖的入口（add_edge(START, "classify") 表示從 classify 開始），END 是出口。條件函式可以直接回傳 END 來結束流程。

    add_conditional_edges 也可以傳第三個參數做對照表：add_conditional_edges("classify", fn, {True: "a", False: "b"})——這樣路由函式可以回傳 True/False 而不是節點名稱字串。

    3人工核准：interrupt

    這是本課的核心機制，也是整個畢業專題最有說服力的部分——一個「知道自己不該擅自做決定」的系統。

    interrupt() 怎麼用

    人工核准節點 · 點標記看說明
    from langgraph.types import interrupt


def request_approval(state: AgentState) -> dict:
    """退款需要人工核准。流程會在這裡凍結。"""
    tx = state["transaction"] or {}

    decision = interrupt({
        "type": "refund_approval",
        "order_id": tx.get("order_id"),
        "amount": tx.get("amount"),
        "currency": tx.get("currency"),
        "reason": state["draft_reply"],
    })

    approved = bool(decision.get("approved"))
    return {
        "refund_approved": approved,
        "trace": [f"人工核准：{'通過' if approved else '駁回'}"],
    }
    1
    interrupt 從 langgraph.types import，不是從 langgraph.graph。
    2
    interrupt(...) 會立刻停止整張圖的執行，把你傳進去的東西回傳給呼叫端。這個 dict 是給「審核的人」看的——要放足夠做決定的資訊（哪一筆、多少錢、為什麼）。
    3
    金額一定要放進來。第 7 週要加「超過某個金額才需要核准」時，這裡就是判斷依據。
    4
    流程恢復時，interrupt() 的回傳值就是你用 Command(resume=...) 傳進來的東西。所以這一行在第一次執行時根本不會跑到——程式在上面就停住了。

    恢復執行

    from langgraph.types import Command

config = {"configurable": {"thread_id": "case-20260401-001"}}

# 第一次執行 —— 會在核准節點停住
result = graph.invoke({"question": user_input, "doc_hits": [], "trace": []}, config=config)

if "__interrupt__" in result:
    payload = result["__interrupt__"][0].value
    print(f"\n需要核准退款")
    print(f"  訂單：{payload['order_id']}")
    print(f"  金額：{payload['currency']} {payload['amount']:,.0f}")
    print(f"  理由：{payload['reason']}")

    answer = input("\n核准嗎？(y/N) ").strip().lower()

    # 用同一個 thread_id 恢復
    result = graph.invoke(
        Command(resume={"approved": answer == "y"}),
        config=config,
    )

print(result["draft_reply"])

    恢復時必須用同一個 thread_id

    thread_id 是 checkpointer 找回狀態的鑰匙。用不同的 id 恢復，LangGraph 會當成一個全新的對話從頭開始——而且不會報錯。

    所以 thread_id 要有意義而且可以查回來：用案件編號、工單號之類的，不要用隨機 UUID 然後忘了存。

    最重要的警告：interrupt 之前的程式碼會重跑

    恢復時，整個節點函式從頭再執行一次

    LangGraph 的 interrupt 不是「從中間那一行繼續」——它是把整個節點重新跑一遍，只是這次 interrupt() 直接回傳你給的值而不再暫停。

    所以 interrupt() 之前的程式碼會執行兩次。如果那裡有副作用（寫資料庫、送通知、扣款、呼叫外部 API），就會發生兩次。

    # ❌ 危險：恢復時會再寄一次信、再寫一筆 log
def request_approval(state):
    send_notification_email(...)          # 第二次執行時又寄一封
    audit_log.insert(...)                 # 又寫一筆重複紀錄
    decision = interrupt({...})
    return {...}


# ✅ 安全做法一：副作用移到 interrupt 之後
def request_approval(state):
    decision = interrupt({...})
    send_notification_email(...)          # 只有恢復後才執行一次
    return {...}


# ✅ 安全做法二：讓副作用冪等（重複執行結果一樣）
def request_approval(state):
    audit_log.upsert(key=f"approval-{state['case_id']}", ...)   # 同 key 不會重複寫
    decision = interrupt({...})
    return {...}

    「冪等（idempotent）」是什麼

    執行一次和執行多次的結果相同。INSERT 不冪等（會變兩筆），UPDATE ... WHERE id = 5 冪等（設成同樣的值幾次都一樣），INSERT ... ON CONFLICT DO NOTHING 也冪等。

    這個概念在第 7 週會再出現一次——退款 API 幾乎都要求你帶一個冪等鍵，就是為了防止網路重試造成重複退款。你在金流的背景應該很熟悉這個。

    4Checkpoint：關掉程式還能接續

    interrupt 只負責「停住」，要能「隔天再繼續」得靠 checkpointer 把狀態存到硬碟。

    選一個 checkpointer

    Checkpointer套件用在哪
    InMemorySaver內建寫測試。程式一關狀態就沒了
    SqliteSaverlanggraph-checkpoint-sqlite本週用這個。存成一個檔案，最簡單
    PostgresSaverlanggraph-checkpoint-postgres第 7 週部署時換這個——你第 3 課已經有 Postgres 在跑了

from langgraph.checkpoint.sqlite import SqliteSaver

checkpointer = SqliteSaver(sqlite3.connect("agent_state.db", check_same_thread=False))
graph = builder.compile(checkpointer=checkpointer)

    之後換成 PostgresSaver 時

    from langgraph.checkpoint.postgres import PostgresSaver

checkpointer = PostgresSaver.from_conn_string(DATABASE_URL)
checkpointer.setup()        # 第一次要建資料表，記得呼叫

    測試「關掉再開」

    這是實作任務明確要求的，而且一定要真的做過一次——很多人以為有 checkpointer 就自動會了。

    # 第一次：跑到核准節點停住，然後直接 Ctrl+C 殺掉程式
uv run python -m agent.cli --thread case-001 --question "A99001 這筆退款給客人"

# 確認狀態真的存進檔案了

# 第二次：全新的程序，只給 thread_id，直接恢復
uv run python -m agent.cli --thread case-001 --resume yes
    def resume_case(thread_id: str, approved: bool) -> None:
    """用 thread_id 把一個暫停中的案件接回來。"""
    config = {"configurable": {"thread_id": thread_id}}

    snapshot = graph.get_state(config)
    if not snapshot.next:
        print("這個 thread 沒有待處理的節點")
        return

    print(f"接續中，下一個節點：{snapshot.next}")
    result = graph.invoke(Command(resume={"approved": approved}), config=config)
    print(result["draft_reply"])

    graph.get_state(config)

    回傳一個 StateSnapshot，裡面有當下的狀態值和 next（接下來要執行哪些節點）。next 是空的表示流程已經結束。

    這個方法在 debug 時非常有用——流程卡住時，先看 get_state 說它停在哪。

    5失敗處理與迴圈防護

    最大步數

    result = graph.invoke(
    {"question": q, "doc_hits": [], "trace": []},
    config={
        "recursion_limit": 25,                       # ← 注意位置
        "configurable": {"thread_id": thread_id},
    },
)

    兩個很容易踩的點

    1. recursion_limit 是 config 的頂層 key，不在 configurable 裡面。放錯位置不會報錯，它只是不生效——然後你的防護等於不存在。
    2. 預設值是 1000 步。這對「避免無限迴圈燒錢」來說形同沒有上限。一定要自己設一個合理的值，本週的流程 25 步綽綽有餘。

    超過上限時會丟 GraphRecursionError，要接起來給使用者一個合理的訊息，不要讓它直接炸到使用者面前。

    三種失敗，三種處理

    失敗處理方式
    工具報錯
    資料庫連不上、API 逾時    		在節點內 try/except，把錯誤寫進 state 的欄位，讓下游節點知道「這一步沒成功」。不要讓例外往上炸掉整張圖
    結果不合理
    查到的交易金額是負數    		用條件邊路由到一個「無法處理」的節點，產生誠實的回覆。不要假裝沒事繼續往下走
    迴圈停不下來recursion_limit，加上在 state 裡自己數次數
     
    def lookup_transaction(state: AgentState) -> dict:
    order_id = state["order_id"]
    if not order_id:
        return {"transaction": None, "error": None,
                "trace": ["查交易：沒有訂單號，略過"]}

    try:
        data = json.loads(get_transaction(order_id))
    except Exception as e:
        # 錯誤變成資料，不是例外
        return {
            "transaction": None,
            "error": f"查詢交易失敗：{type(e).__name__}",
            "trace": [f"查交易：{order_id} → 失敗 {type(e).__name__}"],
        }

    return {"transaction": data if data.get("found") else None, "error": None,
            "trace": [f"查交易：{order_id} → {'找到' if data.get('found') else '查無'}"]}

    「把錯誤變成資料」是 agent 設計的通則

    這和第 2 課的 is_error: True 是同一個思路：讓流程繼續走，但讓後面的節點知道前面出了什麼事，由它們決定怎麼辦。

    直接丟例外會讓整個流程中斷，使用者只看到一個堆疊追蹤——而且你會失去 checkpoint 的價值，因為狀態停在一個無法恢復的地方。

    6狀態與記憶：什麼留 state、什麼進資料庫

    這是設計上很容易弄錯的一塊。原則是問：「這個東西，下一個節點需要嗎？」

    資料放哪為什麼
    使用者的問題、意圖、訂單號State每個節點都要用
    查到的交易、檢索到的段落State擬回覆那一步要用
    執行軌跡 traceState（加 reducer）debug 和稽核用，而且要累積
    完整的文件內容不要放太大。只放 chunk id 和摘要，需要時再查
    歷史案件、稽核日誌資料庫跨 thread 的資料，不屬於這次對話
    使用者偏好、常用設定資料庫要跨對話存活

    State 會被完整存進每一個 checkpoint

    這是為什麼「不要把大東西塞進 state」很重要——每執行一個節點就存一次，state 有多大就寫多少次。把十段文件全文放進 state，跑十個節點就寫了十次。

    更麻煩的是 debug：get_state 印出來會是一大片文字，你找不到真正想看的欄位。

    7手寫迴圈 vs LangGraph

    這是實作任務之一，也是面試一定會問的。先自己想過再看下面——你已經兩種都寫過了，這是你獨有的素材。

    手寫迴圈（第 2 課）LangGraph（本課）
    相依只有 Anthropic SDK多一個框架，要跟著它的版本更新
    看得懂嗎一個 for 迴圈，從上到下讀完就懂要先懂 State/Node/Edge 的概念
    流程可見性藏在控制流裡，畫不出圖結構就是圖，能自動產生流程圖
    暫停與恢復要自己實作，而且很難做對內建 interrupt + checkpoint
    當掉後恢復做不到，只能重跑從上一個 checkpoint 接續
    除錯印 log，自己追get_state 看停在哪、state 長什麼樣
    適合單輪、無狀態、步驟少的任務多步驟、要人工介入、要能恢復的流程

    面試時怎麼講這題

    重點不是「哪個比較好」，而是你能說出取捨點在哪。一個好的回答大概是：

    「我兩種都實作過同一個流程。手寫迴圈在單輪任務上更簡單、相依更少，而且出錯時我完全知道發生什麼事。但我的流程需要在退款時停下來等人核准，而且要能隔天接續——自己實作暫停恢復要處理狀態序列化、版本相容，不如用現成的。所以我的判斷是：如果不需要暫停和恢復，手寫迴圈就夠了；需要的話，框架省下的工作量遠大於它的學習成本。」

    這個回答之所以有力，是因為它基於你真的做過兩次——而不是從部落格文章抄來的比較表。

    用第 4 課的 eval 驗證沒有退步

    換架構是改動最大的一次，一定要量

    你把整個流程從手寫迴圈換成 LangGraph，這是到目前為止最可能無聲無息改壞東西的一次改動。意圖判斷多了一層、節點之間的資訊傳遞可能漏掉東西、prompt 被拆散到各個節點。

    第 4 課建的 eval 腳本現在派上用場了——跑一次，確認品質沒掉。這就是上週做評估的回報：你敢動大刀。

    9自我檢核

    1什麼時候該用固定工作流、什麼時候才該讓模型自主決定？

    原則是能寫死的就寫死——每個「讓模型決定」的環節都是一個不確定性來源，更難測、更難 debug、更貴。

    四個判準要全部成立才值得自主：複雜度（多步驟且無法事先規定）、價值（值得更高成本與延遲）、可行性（模型做得到）、錯誤成本（錯了能被發現並補救）。

    而且要逐個動作判斷，不是整個流程一起決定。本課的設計就是這樣分岔的：擬回覆可以交給模型（錯了有人會看到），執行退款不行（錢出去回不來）——所以退款要人工關卡。

    2State 裡的 trace 欄位每次都只剩最後一筆，為什麼？

    沒有加 reducer。LangGraph 預設的更新規則是覆蓋——節點回傳 {"trace": ["查了交易"]} 就把整欄換掉。

    累積型的欄位要用 Annotated[list[str], add]，更新時才會附加而不是覆蓋。對話訊息可以用現成的 add_messages，或直接繼承 MessagesState。

    3你在核准節點的最前面寄了一封通知信。恢復流程後客戶收到兩封。為什麼？

    因為 interrupt 的恢復機制是「把整個節點重新執行一次」，不是從暫停的那一行繼續。這次 interrupt() 不再暫停、直接回傳你傳入的值，但它之前的程式碼全部會再跑一遍。

    兩個解法：把副作用移到 interrupt() 之後，或讓它冪等（用 upsert、帶冪等鍵）。

    這個概念你在金流應該很熟——退款 API 要求帶冪等鍵就是同一件事。

    4你設了 recursion_limit 但流程還是跑了幾百步。可能哪裡錯了？

    最可能是放錯位置——recursion_limit 是 config 的頂層 key，不能放在 configurable 裡面：

    # ❌ 不生效，而且不報錯
config={"configurable": {"thread_id": "x", "recursion_limit": 25}}

# ✅
config={"recursion_limit": 25, "configurable": {"thread_id": "x"}}

    另外注意預設值是 1000 步，對「避免燒錢」來說等於沒有上限，一定要自己設。

    5哪些東西該放 state，哪些該進資料庫？

    判斷標準是「下一個節點需要嗎」。這次流程中要用的（問題、意圖、查到的交易、檢索結果、trace）放 state；跨對話才有意義的（歷史案件、稽核日誌、使用者偏好）進資料庫。

    還有一條容量上的限制：state 會被完整寫進每一個 checkpoint，所以大東西不要放。文件全文只放 chunk id 和摘要，需要時再查回來——不然跑十個節點就把那堆文字寫了十次，而且 get_state 會變得無法閱讀。

    6既然 LangGraph 功能這麼多，第 2 課的手寫迴圈是不是白寫了？

    不是，而且理由有兩層。

    實務上：如果任務是單輪、無狀態、不需要暫停恢復，手寫迴圈更簡單、相依更少、出錯時你完全知道發生什麼。多裝一個框架是有成本的（學習、版本更新、抽象洩漏）。

    學習上：手寫過才知道 LangGraph 在幫你做什麼、以及它藏起來了什麼。沒寫過的人用框架遇到問題時只能換關鍵字繼續 Google；寫過的人知道底下就是那個 while 迴圈。

    面試時這題的好答案不是選邊站，而是說得出取捨點：需不需要暫停與恢復，就是分界線。

    10常見錯誤排查

    症狀原因與解法
    state 欄位每次只剩最新的一筆累積型欄位沒加 reducer。見 §2。
    節點之間資料對不上 / 欄位是 None初始 state 沒有把所有欄位都給值。LangGraph 不會自動初始化，list 型欄位至少要給 []。
    某個節點把別的節點寫入的東西蓋掉了節點回傳了整個 state 而不是只回傳改動的欄位。
    ImportError: cannot import name 'interrupt'interrupt 在 langgraph.types，不在 langgraph.graph。
    恢復後從頭開始跑thread_id 不一樣。恢復必須用同一個 id，而且不會報錯。見 §3。
    恢復後副作用執行了兩次副作用在 interrupt() 之前。移到後面或讓它冪等。見 §3。
    程式關掉後狀態就沒了用了 InMemorySaver。換成 SqliteSaver 或 PostgresSaver。
    換 PostgresSaver 後報資料表不存在忘了呼叫 checkpointer.setup()。
    recursion_limit 沒作用放進 configurable 裡了。它是頂層 key。見 §5。
    流程卡住不知道停在哪graph.get_state(config) 看 next 是哪些節點。空的表示已結束。
    條件邊永遠走同一條路由函式回傳的字串和 add_node 註冊的名稱對不上。名稱打錯不一定會報錯。
    checkpoint 檔案長得很快state 裡塞了太大的東西（文件全文、完整回應物件）。只存 id 和摘要。見 §6。
    換成 LangGraph 後 eval 分數掉了常見原因：prompt 被拆散到各節點後語境不完整、意圖判斷誤分類、節點之間漏傳欄位。先看 trace 確認走的路徑對不對。
