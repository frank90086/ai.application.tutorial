    LLM API 基本功

    這一課結束時，你能用 Python 呼叫兩家模型、拿到通過驗證的 JSON，並算出每次呼叫花了多少錢、等了多久。這是後面七週所有東西的地基。

    預估時間 8–10 小時 語言 Python 3.12 產出 llm-basics repo 前置知識 無

    0這一課要做到什麼

    先說清楚終點，你才知道中間每一步是為了什麼。

    本週要做的東西是一支命令列工具（CLI）：你在終端機輸入一段「消費者交易申訴」的文字，例如「我上週在網路商店刷了 3,280 元，款項被扣了兩次，到現在都沒退我」，程式呼叫 LLM，然後吐出一段結構化的 JSON：

    {
  "complaint_type": "duplicate_charge",
  "amount": 3280,
  "currency": "TWD",
  "urgency": "high",
  "suggested_action": "核對授權紀錄，確認重複授權後發起退刷",
  "needs_human": true,
  "summary": "消費者反映單筆交易被重複扣款，金額 3,280 元，尚未收到退款。"
}

    看起來很簡單，但要做對的話會踩到五件事，而這五件事正好就是這一課的骨架：

    1. 怎麼把 Python 環境弄乾淨——用 uv，而不是一堆互相打架的 pip 和虛擬環境。
    2. 怎麼跟模型對話——Messages API 的 system / user / assistant 結構，以及一個關鍵觀念：API 沒有記憶。
    3. 怎麼保證輸出一定是合法 JSON——不是在 prompt 裡拜託模型「請輸出 JSON」然後祈禱，而是用 schema 約束它，再用 Pydantic 驗證。
    4. 怎麼知道這通呼叫花了多少錢、等了多久——沒有這個數字，你後面六週都無法判斷任何改動是進步還是退步。
    5. 怎麼在失敗時正確重試——哪些錯該重試、哪些重試一百次也沒用。

    為什麼需要虛擬環境

    Python 預設把套件裝在全域的位置。所以如果你有 A 專案需要 pydantic 1.x、B 專案需要 pydantic 2.x，全域只能有一個版本，兩個專案就會打架。你裝好 B 之後 A 就壞了，而且錯誤訊息通常看不出是版本問題。

    虛擬環境（virtual environment）就是在專案資料夾裡開一個獨立的 Python 環境，裡面有自己的一份套件。啟動它之後，python 和 pip 指向的就是這個資料夾裡的版本，跟系統和其他專案完全無關。資料夾通常叫 .venv/。

    絕對不要把 .venv 提交進 git

    .venv/ 裡面是上千個檔案、幾百 MB，而且綁死你這台機器的路徑和架構（Apple Silicon 編出來的東西在 Linux 上不能跑）。它要被 .gitignore 擋掉。本專案的 .gitignore 已經處理好了。別人要重建環境是靠 pyproject.toml + uv.lock，不是靠你的 .venv。

    uv 是什麼，為什麼用它

    Python 的套件工具歷史上很分裂：pip（裝套件）、venv（建虛擬環境）、pip-tools 或 poetry（鎖版本）、pyenv（管 Python 版本）——四件事四個工具。

    uv 用一個工具做完這四件事，而且用 Rust 寫的，快得很誇張（裝套件通常比 pip 快 10–100 倍）。它還會自動幫你管虛擬環境：你不需要手動 activate，只要用 uv run 執行東西，它就會自動用專案的 .venv。

    型別註解（type hints）

    Python 是動態型別語言，變數不用宣告型別。但從 3.5 開始可以選擇性地標註型別：

    # 沒有註解也能跑
def add(a, b):
    return a + b

# 加上註解：a 和 b 是 int，回傳值是 int
def add(a: int, b: int) -> int:
    return a + b

# 變數也可以註解
name: str = "frank"
amount: float = 3280.0
is_urgent: bool = True

    關鍵：Python 執行時並不檢查型別註解

    上面那個 add(a: int, b: int)，你傳 add("x", "y") 它照跑，回傳 "xy"。註解對 Python 直譯器來說基本上是註解——它只是把資訊存在 __annotations__ 裡，不做任何驗證。

    那為什麼要寫？因為別的工具會讀它：編輯器用它做自動完成和錯誤提示、mypy 這類工具用它做靜態檢查，而Pydantic 用它做真正的執行時驗證。這就是這一課非學不可的原因——我們整個 structured output 都建立在型別註解上。

    常用的複合型別

    # 容器型別（Python 3.9+ 可以直接用小寫內建型別）
names: list[str] = ["a", "b"]            # 字串的 list
scores: dict[str, int] = {"math": 90}    # key 是 str、value 是 int 的 dict
pair: tuple[int, str] = (1, "a")         # 固定長度、固定型別的 tuple

# 可能是 None：用 | None（3.10+ 的寫法）
note: str | None = None                  # 可以是字串，也可以是 None

# 只能是這幾個特定值：Literal
from typing import Literal
level: Literal["low", "medium", "high"] = "high"

    Literal 後面講 structured output 時會大量用到——它是我們告訴模型「緊急度只能是這三個值之一」的方式。

    你可能在舊教材看到的寫法

    舊版 Python 要從 typing import：List[str]、Dict[str, int]、Optional[str]、Union[int, str]。在 3.12 這些還能用（為了相容），但新寫法更乾淨：list[str]、dict[str, int]、str | None、int | str。我們用新寫法。

    dict 與 list 字面值

    呼叫 LLM API 的參數幾乎全是巢狀的 dict 和 list，所以這個要很熟：

    {"role": "user", "content": "你好"},

    外層 [...] 是 list（有順序、可重複），對應其他語言的陣列。這裡順序很重要——它就是對話的時間順序。
    2
    裡面每個 {...} 是 dict（字典 / 鍵值對），對應 JS 的物件、C# 的 Dictionary。"role" 和 "content" 是 key。
    3
    注意最後一個元素後面有逗號。Python 允許這個「尾逗號」，而且是推薦的風格——下次新增一行時 diff 只會多一行，不會動到前一行。

    取值和修改：

    m = {"role": "user", "content": "你好"}

m["role"]                 # "user"  —— 用中括號取值
m["role"] = "assistant"   # 改值
m["extra"] = 123          # 新增 key（dict 可以隨時長出新 key）

m.get("missing")          # None —— key 不存在時回傳 None，不會爆
m["missing"]              # KeyError！—— 直接用中括號取不存在的 key 會丟例外

len(messages)             # 3   —— list 長度
messages[0]               # 第一個元素（從 0 開始算）
messages[-1]              # 最後一個元素（負索引從尾巴算）
messages.append({"role": "user", "content": "再問一個問題"})  # 加到尾巴

    m["key"] vs m.get("key")

    這是新手最常見的執行時錯誤來源。處理 API 回傳的資料時，如果某個欄位可能不存在，用 .get()；如果它一定該存在、不存在就是程式有 bug，用 [] 讓它早點爆掉。早爆比靜默錯誤好。

    amount = 3280
model = "claude-opus-5-5"

# f 開頭的字串，{} 裡面可以放任何運算式
print(f"金額 {amount} 元，用 {model} 處理")

    with 陳述句（context manager）

    這個一定要懂，因為 streaming 的寫法就是 with。

    with 的作用是：保證離開這個區塊時一定會做收尾工作，即使中間發生錯誤。最經典的例子是開檔案：

    # 不好的寫法：如果中間出錯，檔案永遠不會關
f = open("data.txt")
content = f.read()
f.close()          # 如果上一行爆了，這行不會執行

# 好的寫法：離開 with 區塊時，Python 保證幫你呼叫 f.close()
with open("data.txt") as f:
    content = f.read()
# 到這裡檔案一定已經關了，就算 read() 丟了例外也一樣

    Streaming 用同樣的模式，因為串流是一條需要被關閉的網路連線：

    with client.messages.stream(...) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)
# 離開 with 時，SDK 保證把連線關好

    縮排就是程式區塊

    Python 沒有大括號，縮排本身就是語法。with、if、for、def 後面接冒號 :，然後下面縮排的那幾行就是它的區塊。縮排用 4 個空格（不要用 Tab，也不要混用——混用會直接語法錯誤）。編輯器通常會幫你處理好。

    你會在文件和範例裡看到 @ 開頭的東西，知道它在幹什麼就好：

    async / await

    這是本節最抽象的概念，但 LLM 應用繞不過去，因為LLM 呼叫很慢（幾秒到幾十秒），而慢的原因是在等網路，不是在算東西。

    問題：同步程式在等待時完全閒置

    # 同步：一個一個來
result_a = call_llm("申訴 A")   # 等 3 秒
result_b = call_llm("申訴 B")   # 再等 3 秒
result_c = call_llm("申訴 C")   # 再等 3 秒
# 總共 9 秒，而這 9 秒裡 CPU 幾乎沒事做，都在等網路

    解法：async 讓等待的時間可以拿去做別的事

    async 的三個關鍵字 · 點標記看說明
    import asyncio
from anthropic import AsyncAnthropic

client = AsyncAnthropic()

async def call_llm(text: str) -> str:
    response = await client.messages.create(
        model="claude-opus-5-5",
        max_tokens=1024,
        messages=[{"role": "user", "content": text}],
    )
    return response.content[0].text

async def main() -> None:
    results = await asyncio.gather(
        call_llm("申訴 A"),
        call_llm("申訴 B"),
        call_llm("申訴 C"),
    )
    print(results)

asyncio.run(main())
    1
    AsyncAnthropic 是非同步版的客戶端。同步用 Anthropic()、非同步用 AsyncAnthropic()，兩者方法名稱一樣，差別只在要不要 await。
    2
    async def 宣告這是個「協程函式」。呼叫它不會立刻執行，而是回傳一個協程物件，要 await 或交給事件迴圈才會真的跑。
    3
    await 的意思是「這裡要等，但等的時候把控制權交出去，讓別的協程去跑」。只能在 async def 裡面用。
    4
    asyncio.gather(...) 把多個協程同時丟出去跑，全部完成後回傳結果 list，順序和你傳進去的一樣。上面三個呼叫總共約 3 秒，不是 9 秒。
    5
    asyncio.run(main()) 是從「同步世界」進入「非同步世界」的入口。一支程式通常只有這一個地方呼叫它。

    這一課要不要用 async？

    本週的 CLI 是一次處理一筆申訴，用同步的 Anthropic() 就好，程式碼簡單很多。但實作任務裡有一項是「用 10 筆假申訴比較品質、延遲、成本」——那一支批次比較的腳本用 asyncio.gather 會從 30 秒變成 3 秒，很值得。所以兩種都會寫到。

    不要把 API key 傳進 Anthropic()

    你會看到有些教學寫 Anthropic(api_key="sk-ant-...")。能跑，但那個字串很容易跟著程式碼進 git。寫 Anthropic() 就好——SDK 會自己去找 ANTHROPIC_API_KEY 環境變數。少一個出錯的機會。

    三種角色：system / user / assistant

    角色放在哪是什麼誰寫的
    system獨立的 system 參數，不在 messages 裡模型的角色設定、邊界、輸出格式要求你（開發者）
    usermessages 陣列使用者說的話，或你餵給它的資料使用者，或你的程式
    assistantmessages 陣列模型之前的回答模型

    system 不放在 messages 裡，這是 Claude API 和某些其他 API 的差別，值得特別記一下：

    response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    system="你是金流客服助手。只根據使用者提供的資訊回答，不要臆測。",
    messages=[{"role": "user", "content": "我的款項被扣兩次"}],
)

    關鍵觀念：API 完全沒有記憶

    這是最多人第一次用 LLM API 時搞錯的事。

    每一次 messages.create() 都是全新的、互不相關的請求。伺服器端不會記得你上一次問了什麼。你在 Claude 網頁版或 ChatGPT 感受到的「連續對話」，是前端程式每次都把整個對話歷史重新送一遍造出來的錯覺。

    所以多輪對話的程式長這樣——你自己維護一個 list：

    messages = []

while True:
    user_input = input("你： ")
    if user_input.strip() in {"exit", "quit", ""}:
        break

    # 1. 把使用者的話加進歷史
    messages.append({"role": "user", "content": user_input})

    # 2. 把「整個歷史」送出去
    response = client.messages.create(
        model="claude-opus-5-5",
        max_tokens=2048,
        system="你是金流客服助手。",
        messages=messages,
    )

    reply = response.content[0].text
    print(f"助手： {reply}")

    # 3. 把模型的回答也加進歷史，下一輪才有上下文
    messages.append({"role": "assistant", "content": reply})

    漏掉第 3 步是超常見的 bug

    如果你忘記把 assistant 的回答 append 回去，模型下一輪就會完全不記得自己剛剛說過什麼，表現得像失憶。而且因為程式不會報錯，你只會覺得「這模型好笨」。

    更穩的寫法是 messages.append({"role": "assistant", "content": response.content})——直接存整個 content list 而不是只存文字。這樣在有 thinking block 或 tool use 的情況下才不會遺漏資訊，第 2 週手寫 tool-use 迴圈時這點會變成必要條件。

    回傳值的結構：content 是一個 list

    response.content 不是字串，是一個「內容區塊」的 list。每個區塊有 .type，可能是 "text"、"thinking"、"tool_use" 等等。

    所以 response.content[0].text 這種寫法只在最單純的情況下安全。一旦開了思考模式或工具呼叫，第 0 個區塊可能不是文字，這行就會爆。正確的寫法是檢查 type：

    # 脆弱：假設第一個區塊一定是文字
text = response.content[0].text

# 穩健：挑出所有文字區塊
text = "".join(b.text for b in response.content if b.type == "text")

# 或者只要第一個文字區塊
text = next((b.text for b in response.content if b.type == "text"), "")

    完整的回傳物件長這樣：

    response.id            # "msg_01ABC..."  這次呼叫的 ID
response.model          # "claude-opus-5-5"  實際用的模型
response.role           # "assistant"  固定是這個
response.content        # [TextBlock(...), ...]  內容區塊 list
response.stop_reason    # 為什麼停下來（下面詳述）
response.usage          # token 用量，算成本用
response._request_id    # 回報問題給 Anthropic 時要附上這個

    stop_reason：為什麼停下來

    值意思你該怎麼處理
    end_turn正常說完了照常處理
    max_tokens撞到 max_tokens 上限被截斷輸出不完整！JSON 可能解析失敗。要調高上限或縮短任務
    tool_use模型要呼叫工具執行工具、把結果送回去（第 2 週的主題）
    refusal安全機制拒絕了這個請求讀 response.stop_details.category 看原因
    pause_turn長時間執行的伺服器端工具暫停把回傳接回去續跑

    一定要檢查 stop_reason，尤其是做 structured output 時

    max_tokens 截斷是靜默的——HTTP 狀態碼是 200，看起來成功了，但 JSON 少了後半截。如果你直接丟給 json.loads() 就會收到一個看不出原因的解析錯誤。先檢查 stop_reason == "max_tokens"，你就知道是輸出被切掉，不是模型格式寫錯。

    response.stop_details 只有在 stop_reason == "refusal" 時才有值，其他情況是 None——取用前要先判斷，不然會 AttributeError。

    4參數詳解：token、視窗、以及 temperature 的真相

    token 是什麼

    模型不是一個字一個字處理文字，是以 token 為單位。token 大致是「常見的字詞片段」：英文大約 1 token ≈ 4 個字元，中文通常 1 個字就要 1–2 個 token（所以中文的 token 成本比英文高）。

    計價、context window、max_tokens 全都以 token 計算，所以你要能估算。不要用 tiktoken 之類的第三方套件去估 Claude 的 token——那是 OpenAI 的分詞器，數字不對。用官方的計數端點：

    count = client.messages.count_tokens(
    model="claude-opus-5-5",
    system=SYSTEM_PROMPT,
    messages=[{"role": "user", "content": complaint_text}],
)
print(count.input_tokens)   # 這次請求的 input token 數

    這個端點不會真的跑推論，所以不收費。在送出昂貴請求前先估一下很合理。

    max_tokens：輸出的硬上限

    這是必填參數，而且很多人設錯。

    max_tokens 是「輸出」上限，不是「總共」上限

    它只限制模型生成多少 token，和你送進去的 input 無關。而且它是硬切斷——模型不知道這個數字存在，寫到一半被砍掉就是被砍掉，不會自己收尾。這時 stop_reason 會是 max_tokens。

    情境建議值理由
    分類 / 抽取少量欄位256 – 1024輸出本來就短，設小省錢又快
    本課的申訴分類 JSON1024 – 2048夠寫完整個 JSON 加一段摘要
    一般非串流請求~16000SDK 預設 HTTP timeout 下的安全值
    串流請求~64000串流不怕 timeout，給模型空間

    設太小的代價是輸出被截斷要重跑（反而更貴）；設太大的代價只是「允許」它寫長，實際計費是照真正生成的 token 數，不是照上限。所以寧可寬鬆一點。

    context window：輸入 + 輸出的總容量

    Context window 是模型一次能「看到」的總 token 數——system prompt + 整個 messages 歷史 + 這次要生成的輸出，全部加起來不能超過。

    模型模型 IDContext window最大輸出
    Claude Opus 5.5claude-opus-5-51M128K
    Claude Sonnet 5.5claude-sonnet-5-51M128K
    Claude Haiku 4.5claude-haiku-4-5200K—

    1M token 大約是 70 萬字的中文，實務上很難撞到。但撞到之前你會先被成本嚇到——送 1M token 進 Opus 5.5 一次就是 4 美金。這是第 6 週要做可觀測性的原因之一。

    temperature：這個參數在現行 Claude 模型上已經不存在了

    這是本課最重要的「別照舊教學做」

    幾乎所有 2024–2025 年的 LLM 教學都會教你用 temperature 控制輸出的隨機性：0 比較固定、1 比較有創意。在現行的 Claude 模型上，送出 temperature 會直接收到 HTTP 400 錯誤。top_p 和 top_k 也一樣被移除了。

    模型temperature / top_p / top_k
    claude-opus-5-5、claude-opus-5已移除，送出回 400
    claude-sonnet-5-5只接受預設值，給非預設值回 400
    claude-haiku-4-5仍可使用
    OpenAI 的模型仍可使用（所以做雙供應商抽象時要注意）

    那現在用什麼控制？output_config.effort

    新的控制軸不是「隨機性」，是思考深度與 token 花費：

    response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=2048,
    output_config={"effort": "low"},   # low | medium | high | xhigh | max
    messages=[{"role": "user", "content": complaint_text}],
)
    effort適用
    low分類、抽取、簡單改寫、子代理。本課的申訴分類從這裡開始試
    medium需要一點判斷的任務。claude-opus-5-5 的預設值
    high需要推理的工作。claude-sonnet-5-5 的預設值
    xhigh / max困難的程式與長流程代理工作，正確性比成本重要時

    成本優化的第一個旋鈕

    很多人想省錢的第一反應是「換成小模型」。但先試「同一個模型降低 effort」——新模型在低 effort 下常常還是勝過上一代在高 effort 下的表現，而且維持單一模型有額外好處（prompt cache 是綁模型的，混用模型就無法共用快取）。這也是本週比較表該量的東西之一。

    thinking：思考模式

    現行模型的「擴展思考」是自適應的，模型自己決定要想多久：

    response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=4096,
    thinking={"type": "adaptive", "display": "summarized"},
    output_config={"effort": "high"},
    messages=[{"role": "user", "content": "這筆交易的錯誤碼 05 代表什麼，該怎麼處理？"}],
)

for block in response.content:
    if block.type == "thinking":
        print("[思考]", block.thinking)
    elif block.type == "text":
        print("[回答]", block.text)

    三個容易踩的點

    • claude-opus-5-5 的思考永遠開著，不能關。送 {"type": "disabled"} 或 budget_tokens 都會回 400。要少花錢就降低 effort。
    • budget_tokens 是舊寫法。舊教學會教 thinking={"type": "enabled", "budget_tokens": 10000}，在現行模型上一律 400。只有 Haiku 4.5 這類較舊的模型還用這個。
    • display 預設是 "omitted"——思考照樣發生、照樣計費，但 block.thinking 會是空字串。想看到摘要要明確寫 "summarized"。如果你在做串流 UI，不設這個會讓使用者看到一段長長的空白才開始有輸出。

    完整的參數對照表

    參數必填說明
    model是模型 ID 字串。不要自己加日期後綴，claude-opus-5-5 就是完整的 ID
    max_tokens是輸出上限
    messages是對話歷史 list
    system否系統提示，獨立參數
    output_config否{"effort": ...} 控制深度、{"format": ...} 約束輸出格式
    thinking否{"type": "adaptive", "display": "summarized"}
    tools否工具定義（第 2 週）
    stream否低階串流開關，但建議用 messages.stream() 輔助方法
    temperature—已移除 見上方
    output_format—已棄用 create() 上的這個參數被 output_config.format 取代了

    5Structured Output 與 Pydantic

    這是本週的技術核心，也是「能跑的 demo」和「能上線的系統」之間最大的分界線。

    為什麼不能只在 prompt 裡拜託模型

    新手的第一個做法通常是這樣：

    # 這個做法會在半夜叫你起來修 bug
response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    system="請用 JSON 格式回答，包含 complaint_type、amount、urgency 三個欄位。",
    messages=[{"role": "user", "content": complaint}],
)
data = json.loads(response.content[0].text)   # 💥

    這在 95% 的情況會成功，然後在剩下 5% 用各種方式失敗：

    • 模型在 JSON 前後加了說明文字：好的，以下是分析結果：{...}
    • 包在 markdown 程式碼區塊裡：```json\n{...}\n```
    • 欄位名稱自己換了：type 而不是 complaint_type
    • amount 回傳字串 "3280" 而不是數字 3280
    • urgency 回傳 "很高" 而不是你預期的 "high"
    • 撞到 max_tokens 被截斷，JSON 少了尾巴

    而 5% 的失敗率在一個每天處理 1000 筆申訴的系統裡，就是每天 50 筆錯誤。

    正確的做法有兩層：

    1. 用 schema 從 API 層面約束輸出——讓「不合法的 JSON」在生成階段就不可能發生。
    2. 用 Pydantic 在程式裡驗證——確保欄位齊全、型別正確、值在允許範圍內，失敗就重試。

    Pydantic 是什麼

    Pydantic 把第 2 節講的型別註解變成真正會執行的驗證。你用熟悉的 class 語法描述資料長什麼樣，它負責檢查、轉換、和報錯。

    Pydantic 的基本結構 · 點標記看說明
    from pydantic import BaseModel, Field, ValidationError

class Complaint(BaseModel):
    complaint_type: str
    amount: float = Field(ge=0)
    urgency: str = "medium"
    note: str | None = None

c = Complaint(complaint_type="duplicate_charge", amount="3280")
print(c.amount)        # 3280.0  —— 字串被自動轉成 float
print(c.urgency)       # "medium"  —— 用了預設值
print(c.model_dump())  # 轉回 dict
    1
    繼承 BaseModel 就得到驗證能力。類別名稱用大駝峰是 Python 慣例。
    2
    最單純的欄位：名稱 + 型別。沒有預設值表示必填，缺了就丟 ValidationError。
    3
    Field(ge=0) 加額外約束，ge 是 greater-or-equal。常用的還有 gt、le、lt、min_length、max_length、pattern（正規表示式）。這也是放欄位說明的地方，等一下會用到。
    4
    有預設值 = 選填。模型沒給就用 "medium"。
    5
    str | None = None 表示「可以是字串也可以是 None，預設 None」。這是表達「這個欄位可能沒有值」的標準寫法。
    6
    注意這裡傳的是字串 "3280"，但 Pydantic 看到欄位型別是 float，自動幫你轉成 3280.0。這解決了前面列的「amount 回傳字串」問題。
    7
    model_dump() 把物件轉回普通 dict（要 JSON 字串就用 model_dump_json()）。注意：Pydantic 1.x 的方法叫 .dict() 和 .json()，2.x 改名了，舊教學的寫法在新版會有棄用警告。

    驗證失敗時會發生什麼

    try:
    Complaint(complaint_type="duplicate_charge", amount=-50)
except ValidationError as e:
    print(e)
# 1 validation error for Complaint
# amount
#   Input should be greater than or equal to 0 ...

    ValidationError 的訊息非常詳細——它告訴你哪個欄位、為什麼不合格。這點很重要，因為我們等一下要把這個錯誤訊息餵回模型讓它自己修正。

    設計申訴分類的 schema

    現在來設計本週真正要用的資料結構。這裡每個決定都有理由：

    from enum import Enum
from pydantic import BaseModel, Field


class ComplaintType(str, Enum):
    """申訴類型。用 Enum 而不是自由字串，模型就只能回這幾個值。"""
    DUPLICATE_CHARGE = "duplicate_charge"      # 重複扣款
    UNAUTHORIZED = "unauthorized"              # 未授權交易
    REFUND_NOT_RECEIVED = "refund_not_received"  # 退款未入帳
    WRONG_AMOUNT = "wrong_amount"              # 金額錯誤
    FAILED_PAYMENT = "failed_payment"          # 交易失敗
    OTHER = "other"                            # 其他


class Urgency(str, Enum):
    LOW = "low"
    MEDIUM = "medium"
    HIGH = "high"


class ComplaintAnalysis(BaseModel):
    """一筆消費者交易申訴的分析結果。"""

    complaint_type: ComplaintType = Field(
        description="申訴屬於哪一類。無法判斷時用 other。"
    )
    amount: float | None = Field(
        default=None,
        ge=0,
        description="申訴涉及的金額。申訴文字沒提到金額時必須為 null，不要猜。",
    )
    currency: str | None = Field(
        default=None,
        description="三位字母的貨幣代碼，例如 TWD、USD。沒提到就 null。",
    )
    urgency: Urgency = Field(
        description="緊急度。涉及未授權交易或金額超過 10000 時為 high。"
    )
    needs_human: bool = Field(
        description="是否需要轉人工處理。涉及退款、爭議款項時為 true。"
    )
    suggested_action: str = Field(
        max_length=200,
        description="建議客服執行的下一步，一句話，繁體中文。",
    )
    summary: str = Field(
        max_length=300,
        description="用一到兩句繁體中文摘要這筆申訴。",
    )
    missing_info: list[str] = Field(
        default_factory=list,
        description="要處理這筆申訴還缺哪些資訊，例如訂單號、交易時間。沒缺就空陣列。",
    )

    三個設計重點，每個都有理由

    • description 是給模型看的，不是給人看的。它會被翻譯成 JSON Schema 送進 API，模型讀得到。所以這裡要寫得像指令——「沒提到金額時必須為 null，不要猜」比「金額」有用一百倍。這是對抗幻覺最便宜的手段。
    • 用 Enum 而不是 str。這樣模型回不出 "很高" 或 "URGENT"——schema 本身就限制了可能的值，你的下游程式可以放心用 if urgency == Urgency.HIGH 比對。
    • missing_info 用 default_factory=list 而不是 = []。這是 Python 的一個經典陷阱：可變的預設值（list、dict）如果直接寫 = []，所有實例會共用同一個 list，一個改到全部都改。Pydantic 會幫你擋下這個寫法，但一般的 Python 函式不會，所以養成習慣。

    做法一：messages.parse()（推薦）

    SDK 提供一個輔助方法，把「送 schema 進去 + 驗證回來的 JSON」一次做完：

    本週的核心呼叫 · 點標記看說明
    import anthropic
from models import ComplaintAnalysis

client = anthropic.Anthropic()

SYSTEM = """你是金流客服的申訴分析助手。

規則：
- 只根據申訴文字中明確提到的資訊填寫欄位，不要推測或補完。
- 申訴文字沒提到的欄位，留空或填 null。
- 無法判斷類型時使用 other，不要勉強歸類。"""


def analyze(complaint: str) -> ComplaintAnalysis:
    response = client.messages.parse(
        model="claude-opus-5-5",
        max_tokens=2048,
        system=SYSTEM,
        output_config={"effort": "low"},
        messages=[{"role": "user", "content": complaint}],
        output_format=ComplaintAnalysis,
    )
    return response.parsed_output
    1
    messages.parse() 而不是 messages.create()。它是 create() 的包裝，多做了 schema 轉換和驗證。
    2
    分類任務用 low effort 起步，省錢又快。之後跑比較表時可以試不同的值看品質差多少。
    3
    這裡的 output_format 是 parse() 的參數，直接傳 Pydantic 類別——它會自動產生 JSON Schema 送給 API。注意不要跟下面那個已棄用的東西搞混。
    4
    response.parsed_output 是已經驗證過的 ComplaintAnalysis 實例，不是字串也不是 dict。你可以直接 result.urgency、result.amount，編輯器還會自動完成。

    兩個 output_format 很容易搞混

    • client.messages.parse(..., output_format=MyModel) — 正確 這是 parse 輔助方法的參數，傳 Pydantic 類別。
    • client.messages.create(..., output_format=...) — 已棄用 create() 上的這個頂層參數已被 output_config={"format": {...}} 取代。

    名字一樣但不是同一個東西。記住：用 parse() 就傳 output_format=模型類別；用 create() 就寫 output_config={"format": {...}}。

    做法二：output_config.format 手寫 schema

    如果你不想用 Pydantic，或需要動態產生 schema：

    import json

response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=2048,

    做法三：strict tool use

    第三種方式是定義一個工具，用 strict: True 保證參數符合 schema：

    做法什麼時候用
    parse() + Pydantic只是要拿一份結構化資料。本課用這個
    output_config.formatschema 要在執行時動態組出來，或不想引入 Pydantic
    strict tool use模型要「做一件事」而不只是「回一份資料」，而且可能有多個工具可選。第 2 週的主題

    不要用 tool_choice 強迫模型呼叫工具

    舊教學常見的技巧是用 tool_choice={"type": "tool", "name": "..."} 強制模型一定要呼叫某個工具，藉此拿到結構化輸出。在 claude-opus-5-5 和 claude-sonnet-5-5 上，tool_choice 的 any 和 tool 會回 400。如果那個強制呼叫本來只是為了拿 JSON，直接改用 structured output 才是對的解法。

    驗證失敗時重試

    就算有 schema 約束，還是有失敗情境：撞到 max_tokens 被截斷、或是通過了 schema 但違反你的業務規則（例如 amount 是負數）。所以本週的實作任務要求「驗證失敗就重試」。

    關鍵技巧是把 ValidationError 的內容原封不動餵回模型——它的訊息已經寫得很清楚哪裡錯了：

    from pydantic import ValidationError

def analyze_with_retry(complaint: str, max_attempts: int = 3) -> ComplaintAnalysis:
    messages: list[dict] = [{"role": "user", "content": complaint}]

    for attempt in range(1, max_attempts + 1):
        response = None
        try:
            response = client.messages.parse(
                model="claude-opus-5-5",
                max_tokens=2048,
                system=SYSTEM,
                output_config={"effort": "low"},
                messages=messages,
                output_format=ComplaintAnalysis,
            )

            # 先檢查是不是被截斷 —— 這會讓 JSON 不完整
            if response.stop_reason == "max_tokens":
                raise RuntimeError(
                    f"輸出被 max_tokens 截斷（第 {attempt} 次）。調高 max_tokens。"
                )

            return response.parsed_output

        except ValidationError as e:
            if attempt == max_attempts:
                raise

            # 把模型的錯誤回答和驗證錯誤一起送回去，讓它自己修。
            # response 可能是 None（驗證在 parse() 內就失敗），那就只送錯誤訊息。
            if response is not None:
                messages.append({"role": "assistant", "content": response.content})
            messages.append({
                "role": "user",
                "content": (
                    f"你上一次的回答沒有通過驗證：\n{e}\n\n"
                    "請依照 schema 重新輸出，只修正出錯的欄位。"
                ),
            })

    raise RuntimeError("不會走到這裡")

    try 要包住整個 parse()，不能只包取值那一行

    直覺的寫法是 response = client.messages.parse(...) 放在 try 外面、只把 return response.parsed_output 包起來。但驗證有可能是在 parse() 內部就執行並拋出的——那樣例外會從 try 外面飛出去，你的重試邏輯一次都不會觸發，而且表面上看起來只是「這個 API 有時候會丟 ValidationError」。

    把整段包進 try 的寫法兩種情況都成立，所以不需要先確認 SDK 是哪一種行為。這是處理不確定的函式庫行為時的通用做法：讓程式對兩種可能都正確，而不是賭一種。

    代價是 response 可能是 None（在 parse 內就失敗時），所以 append 前要先判斷。

    為什麼要把錯誤訊息送回去

    因為這等於給模型一個具體的、機器產生的回饋，而不是含糊的「你錯了請重試」。實務上第二次就成功的比例很高。這個「驗證 → 回饋 → 重試」的迴圈是 LLM 應用的基本模式，第 5 週做 agent 時會用同一個思路處理工具呼叫失敗。

    注意 messages.append({"role": "assistant", "content": response.content}) 存的是整個 content list，不是文字——這就是第 3 節提到的穩健寫法。

    6Streaming：使用者感受到的速度

    一個 LLM 請求要 5 秒才回完。使用者的體感有兩種：

    • 不串流：盯著空白畫面 5 秒，然後整段文字一次出現。感覺很慢。
    • 串流：0.4 秒後第一個字出現，然後逐字長出來。感覺很快——即使總時間完全一樣。

    所以「延遲」要量兩個數字：TTFT（time to first token，第一個 token 的時間）和總時間。本週的比較表應該兩個都記。

    基本寫法

    with client.messages.stream(
    model="claude-opus-5-5",
    max_tokens=4096,
    system=SYSTEM,
    messages=[{"role": "user", "content": complaint}],
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)

    兩個細節：

    • with 是必要的（第 2 節講過）——串流是一條網路連線，要保證關閉。
    • flush=True 是必要的。Python 的 print 預設會把輸出先放在緩衝區，攢一批才真的寫出去。不加 flush=True 你會看到文字一塊一塊跳出來，串流的意義就沒了。end="" 則是不要每次都換行。

    量 TTFT

    import time

start = time.perf_counter()
ttft = None

with client.messages.stream(
    model="claude-opus-5-5",
    max_tokens=4096,
    messages=[{"role": "user", "content": complaint}],
) as stream:
    for text in stream.text_stream:
        if ttft is None:
            ttft = time.perf_counter() - start    # 第一個 token 到的時間
        print(text, end="", flush=True)

    final = stream.get_final_message()            # 拿完整的回傳物件

total = time.perf_counter() - start
print(f"\n\nTTFT {ttft * 1000:.0f} ms / 總計 {total * 1000:.0f} ms")
print(f"輸出 {final.usage.output_tokens} tokens")

    time.perf_counter() 而不是 time.time()

    time.time() 回傳的是「牆上時鐘」，會被系統時間調整（NTP 校時、夏令時間）影響，拿來量短時間間隔可能出現負數。量時間間隔一律用 time.perf_counter()，它是單調遞增的高解析度計時器。

    get_final_message()：串流也要拿得到完整物件

    stream.get_final_message() 回傳的東西和非串流的 create() 一模一樣——有 usage、stop_reason、完整的 content。所以你不會因為用了串流就失去算成本的能力。

    如果你只是想避開大 max_tokens 的 HTTP timeout、根本不需要逐字顯示，可以這樣寫：

    # 用串流傳輸，但不逐字處理，只要最後結果
with client.messages.stream(model=..., max_tokens=64000, messages=...) as stream:
    response = stream.get_final_message()

    max_tokens 很大時必須用串流

    SDK 的 HTTP timeout 預設 10 分鐘。如果你設 max_tokens=64000 又用非串流的 create()，長輸出可能撞到 timeout 整個失敗。超過 ~16000 就改用 .stream()。

    串流 + 思考模式

    開了 thinking 之後，串流會送出兩種 delta，要分開處理：

    with client.messages.stream(
    model="claude-opus-5-5",
    max_tokens=8192,
    thinking={"type": "adaptive", "display": "summarized"},
    messages=[{"role": "user", "content": question}],
) as stream:
    for event in stream:
        if event.type == "content_block_start":
            if event.content_block.type == "thinking":
                print("\n[思考中…]\n")
            elif event.content_block.type == "text":
                print("\n[回答]\n")
        elif event.type == "content_block_delta":
            if event.delta.type == "thinking_delta":
                print(event.delta.thinking, end="", flush=True)
            elif event.delta.type == "text_delta":
                print(event.delta.text, end="", flush=True)

    注意這裡迭代的是 stream 本身（拿到事件物件），而不是 stream.text_stream（只拿文字）。要細緻控制就迭代 stream，只要文字就用 text_stream。

    把量測寫進程式

    import time
from dataclasses import dataclass

# 每 1M token 的價格（USD）
PRICING = {
    "claude-opus-5-5":   {"in": 4.00, "out": 20.00},
    "claude-sonnet-5-5": {"in": 2.00, "out": 10.00},
    "claude-haiku-4-5":  {"in": 1.00, "out":  5.00},
}


@dataclass
class CallResult:
    """一次呼叫的量測結果。"""
    model: str
    input_tokens: int
    output_tokens: int
    latency_ms: float
    cost_usd: float
    output: ComplaintAnalysis | None
    error: str | None = None


def cost_of(model: str, input_tokens: int, output_tokens: int) -> float:
    p = PRICING[model]
    return (input_tokens * p["in"] + output_tokens * p["out"]) / 1_000_000


def measured_analyze(model: str, complaint: str) -> CallResult:
    start = time.perf_counter()
    try:
        response = client.messages.parse(
            model=model,
            max_tokens=2048,
            system=SYSTEM,
            messages=[{"role": "user", "content": complaint}],
            output_format=ComplaintAnalysis,
        )
    except Exception as e:
        return CallResult(
            model=model, input_tokens=0, output_tokens=0,
            latency_ms=(time.perf_counter() - start) * 1000,
            cost_usd=0.0, output=None, error=f"{type(e).__name__}: {e}",
        )

    latency_ms = (time.perf_counter() - start) * 1000
    u = response.usage
    return CallResult(
        model=model,
        input_tokens=u.input_tokens,
        output_tokens=u.output_tokens,
        latency_ms=latency_ms,
        cost_usd=cost_of(model, u.input_tokens, u.output_tokens),
        output=response.parsed_output,
    )

    @dataclass 是什麼

    它幫你自動產生 __init__、__repr__ 這些樣板程式碼。@dataclass 和 Pydantic 的 BaseModel 很像，差別是：@dataclass 不做驗證（只是方便的資料容器），Pydantic 會驗證。

    所以原則是：資料來自外部（LLM、API、使用者輸入）就用 Pydantic；資料是你自己程式內部算出來的就用 @dataclass。上面的 CallResult 是我們自己算的，不需要驗證。

    為什麼開發時要用小模型

    你在開發階段會跑同一組測試幾十次。假設你的 10 筆測試每次呼叫 input 800 / output 300 token：

    跑一輪 10 筆跑 50 輪
    claude-opus-5-5$0.092$4.60
    claude-haiku-4-5$0.023$1.15

    金額都不大，但這只是第 1 週、10 筆測試。到第 6 週你會有 20 個端到端情境、每個情境裡 agent 會呼叫模型好幾次，而且每改一次 prompt 就要全部重跑。到那時這個比例會變成有感的差距，所以現在就養成習慣：開發和跑迴歸測試用小模型，只在做品質比較時才呼叫大模型。

    8錯誤處理與重試

    先知道 SDK 已經幫你做了什麼

    不要急著自己寫 backoff

    Anthropic 的 Python SDK 預設就會自動重試連線錯誤、408、409、429 和 5xx，而且用的就是指數退避。預設重試 2 次。

    所以第一步不是寫重試邏輯，是把內建的次數調成你想要的：

    # 在客戶端層級設定
client = anthropic.Anthropic(max_retries=5, timeout=30.0)

# 或針對單一呼叫覆寫，不動到 client
response = client.with_options(max_retries=1).messages.create(...)

# max_retries=0 完全關閉自動重試（想自己完全控制時）
client = anthropic.Anthropic(max_retries=0)

    timeout 會乘上重試次數

    Timeout 本身也算可重試的錯誤。所以最壞情況的總等待時間是 timeout × (max_retries + 1)。timeout=30, max_retries=5 代表最久可能卡 3 分鐘。做 CLI 或 API 服務時要把這個算進去。

    例外類別：從最specific到最general

    import anthropic

try:
    response = client.messages.create(...)

except anthropic.BadRequestError as e:
    # 400 —— 你的請求有問題。重試一萬次也一樣。
    # 常見原因：送了 temperature、budget_tokens、用了不存在的參數
    print(f"請求格式錯誤：{e.message}")
    raise

except anthropic.AuthenticationError:
    # 401 —— API key 錯了或沒設。不要重試。
    print("API key 無效，檢查 .env 和環境變數")
    raise

except anthropic.NotFoundError:
    # 404 —— 模型 ID 打錯了。不要重試。
    print("模型 ID 不存在，檢查有沒有多加日期後綴")
    raise

except anthropic.RateLimitError as e:
    # 429 —— 超過速率限制。可以重試，而且伺服器告訴你要等多久。
    retry_after = int(e.response.headers.get("retry-after", "60"))
    print(f"觸發速率限制，{retry_after} 秒後重試")

except anthropic.APIStatusError as e:
    # 其他有 HTTP 狀態碼的錯誤
    if e.status_code >= 500:
        print(f"伺服器錯誤 {e.status_code}，可以重試")
    else:
        print(f"客戶端錯誤 {e.status_code}，不該重試：{e.message}")
        raise

except anthropic.APIConnectionError:
    # 根本沒連上 —— 網路問題。可以重試。
    print("連線失敗，檢查網路")

    不要只 catch 一個大類別

    很多人圖方便寫 except anthropic.APIStatusError: 就打包全部。這會把「該重試的」和「重試一萬次也沒用的」混在一起——你的程式會對著一個 400 錯誤重試五次、等三十秒，然後回報同一個錯。

    記住這個分界：429 和 5xx 和連線錯誤可以重試；其他 4xx 是你的 bug，要讓它爆出來。

    自己寫指數退避（當內建的不夠用時）

    實作任務要求你加上錯誤重試，而且要理解它的原理。這是標準寫法：

    指數退避 + jitter · 點標記看說明
    import random
import time
import anthropic


def call_with_retry(
    client: anthropic.Anthropic,
    max_attempts: int = 5,
    base_delay: float = 1.0,
    max_delay: float = 60.0,
    **kwargs,
):
    last_error: Exception | None = None

    for attempt in range(max_attempts):
        try:
            return client.messages.create(**kwargs)

        except anthropic.RateLimitError as e:
            last_error = e
        except anthropic.APIConnectionError as e:
            last_error = e
        except anthropic.APIStatusError as e:
            if e.status_code < 500:
                raise
            last_error = e

        if attempt == max_attempts - 1:
            break

        backoff = base_delay * (2 ** attempt)
        jitter = random.uniform(0, 1)
        delay = min(backoff + jitter, max_delay)
        print(f"第 {attempt + 1}/{max_attempts} 次失敗，{delay:.1f} 秒後重試")
        time.sleep(delay)

    raise last_error
    1
    **kwargs 把所有其他關鍵字參數打包成 dict，原封不動傳給 messages.create()。這樣這個包裝函式不需要知道有哪些參數，create() 加新參數也不用改它。
    2
    只有可重試的錯誤才記下來繼續；4xx（除了 429）直接 raise 往外丟，不浪費時間。
    3
    2 ** attempt 是指數退避的核心：等待時間變成 1、2、4、8、16 秒。為什麼要指數成長？因為如果伺服器正在過載，固定間隔的重試只會持續加重它的負擔。
    4
    random.uniform(0, 1) 是 jitter（抖動），加一點隨機。沒有它的話，同時失敗的 100 個請求會在完全同一秒一起重試，造成新的尖峰，然後一起再失敗——這叫 thundering herd（驚群效應）。加一點隨機就能把它們打散。
    5
    min(..., max_delay) 設上限，不然第 10 次重試要等 1024 秒。
    6
    注意這裡用 break 而不是在迴圈裡 sleep——最後一次失敗後不需要再等，直接丟出例外。這是很常見的 off-by-one bug。

    如果錯誤回應裡有 retry-after，優先用它

    429 回應的 header 通常有 retry-after，那是伺服器告訴你的準確等待時間，比你自己算的指數退避精準。有就用它，沒有才退回自己算。

    9雙供應商切換

    實作任務要求「同一支程式可切換供應商」。這不只是練習——它是你在面試時能回答「你怎麼決定用哪個模型」的基礎，而且第 6 週要「用測試結果決定要不要換模型」時，這個抽象層就是前提。

    設計原則：抽象「你的需求」，不要抽象「API 的全部功能」

    新手最常見的過度設計

    不要試著做一個「支援所有供應商所有參數」的通用包裝層。各家的參數差異很大（例如 Claude 現行模型沒有 temperature，OpenAI 有），硬要統一只會做出一個到處都是 if provider == ... 的怪物。

    正確做法是定義「你的應用需要什麼」——在這個專案裡就是「給我一段申訴文字，回我一個驗證過的 ComplaintAnalysis」。介面就這麼窄，各家自己想辦法滿足它。

        u = response.usage
        return CallResult(
            model=self.model,
            input_tokens=u.input_tokens,
            output_tokens=u.output_tokens,
            latency_ms=(time.perf_counter() - start) * 1000,
            cost_usd=cost_of(self.model, u.input_tokens, u.output_tokens),
            output=response.parsed_output,
        )

    Protocol 是什麼

    Protocol 是 Python 的「結構化型別」機制，概念接近 Go 的 interface 或 TypeScript 的 interface：你不需要明確繼承它，只要你的類別剛好有 name 屬性和 analyze() 方法，型別檢查工具就認定它符合 Analyzer。

    這和 C# 的 interface 不同——C# 要寫 class Foo : IAnalyzer，Python 的 Protocol 只看「長得像不像」（鴨子型別的靜態檢查版本）。

    12自我檢核

    這些都是面試會問的。先自己想過再看答案。

    1為什麼 LLM API 的多輪對話要自己維護 messages 陣列？這對成本有什麼影響？

    因為 API 是無狀態的——伺服器不記得前一次請求。「連續對話」是客戶端每次把完整歷史重送造成的效果。

    成本影響：對話越長，每次請求的 input token 越多，成本隨對話長度成長（而且是每一輪都付一次完整歷史的錢）。這就是 prompt caching 存在的理由——把不變的前綴快取起來，重複讀取只要約 0.1 倍價格。

    2你照著某篇 2025 年的教學寫了 temperature=0，結果收到 400 錯誤。發生什麼事？現在該用什麼？

    temperature（以及 top_p、top_k）在現行 Claude 模型上已經移除，送出會被拒絕。claude-opus-5-5 和 claude-opus-5 直接 400；claude-sonnet-5-5 只接受預設值。

    取代它的控制軸是 output_config={"effort": ...}，從 low 到 max，控制的是思考深度與 token 花費而不是隨機性。注意 claude-haiku-4-5 和 OpenAI 的模型還有 temperature——這是做雙供應商抽象層時要小心的地方。

    3你的 structured output 有 schema 約束了，為什麼還需要 Pydantic 驗證和重試？

    schema 保證「JSON 語法合法、欄位符合型別」，但不保證：

    • 沒被截斷——撞到 max_tokens 時 HTTP 仍是 200，JSON 卻少了尾巴。要檢查 stop_reason。
    • 符合業務規則——schema 說 amount 是數字，但「金額不能是負數」、「未授權交易的 urgency 必須是 high」這類規則要靠 Pydantic 的 Field 約束或自訂驗證器。
    • 內容正確——模型可能把金額看錯、把類型分錯。這要靠 evals（第 4、6 週）。

    schema 擋格式問題，Pydantic 擋語意問題，evals 擋正確性問題。三層是不同的事。

    4哪些錯誤該重試，哪些不該？為什麼重試要加 jitter？

    該重試：429（速率限制）、5xx（伺服器錯誤）、連線錯誤、timeout。這些是暫時性的。

    不該重試：400（請求格式錯）、401（key 無效）、404（模型 ID 錯）。這些是你的 bug，重試一萬次結果一樣，只是浪費時間並掩蓋問題。

    jitter：如果 100 個請求同時被限流，沒有隨機抖動的話它們會在完全同一秒一起重試，造成新的尖峰然後一起再失敗（thundering herd）。加一點隨機把它們打散。

    另外：Anthropic SDK 預設已經會重試 429/5xx/連線錯誤，先用 max_retries 調整內建行為，不要急著自己寫一套。

    5response.content[0].text 什麼時候會爆掉？

    content 是內容區塊的 list，第 0 個不一定是文字。開了 thinking 模式時第 0 個可能是 thinking block，有工具呼叫時可能是 tool_use block——這兩種都沒有 .text 屬性，會丟 AttributeError。

    穩健寫法是過濾 type：next((b.text for b in response.content if b.type == "text"), "")。

    6為什麼 output token 比 input token 貴，這對設計有什麼影響？

    現行模型 output 大約是 input 的 5 倍價格（例如 Opus 5.5 是 $4 vs $20 /1M）。原因是生成是逐 token 自迴歸的，無法像讀取輸入那樣平行處理。

    設計影響：讓模型少講話的效益遠大於讓它少讀東西。所以——要求簡潔的輸出格式、不要叫模型重複輸入內容、用 enum 代替自由文字、分類任務的 max_tokens 設小。至於「少讀東西」那一側，更有效的手段是 prompt caching 而不是刪減上下文。

    13常見錯誤排查

    症狀原因與解法
    ModuleNotFoundError: No module named 'anthropic' 你用系統的 python 跑而不是專案環境。一律用 uv run python ...，不要直接 python ...。
    AuthenticationError / 401 依序檢查：.env 存在嗎？有呼叫 load_dotenv() 嗎？變數名稱是 ANTHROPIC_API_KEY 嗎（不是 CLAUDE_API_KEY）？key 有沒有多複製到空白或換行？
    BadRequestError，訊息提到 temperature 現行 Claude 模型已移除此參數。拿掉它，需要控制深度就用 output_config={"effort": ...}。見 §4。
    BadRequestError，訊息提到 budget_tokens 舊的思考預算寫法。改成 thinking={"type": "adaptive"}。
    NotFoundError / 404 模型 ID 錯。最常見是自己加了日期後綴——claude-opus-5-5 就是完整 ID，不要寫成 claude-opus-5-5-20260401。
    JSON 解析失敗，但 HTTP 是 200 幾乎都是撞到 max_tokens 被截斷。檢查 response.stop_reason，是 "max_tokens" 就調高上限。
    AttributeError: 'ThinkingBlock' object has no attribute 'text' 用了 content[0].text 但第 0 個區塊是思考區塊。改用 type 過濾。見 §3。
    模型「忘記」前面說過的話 忘記把 assistant 的回答 append 回 messages。見 §3。
    串流的文字一塊一塊跳出來 print 少了 flush=True，輸出被緩衝住了。
    思考模式開了但 block.thinking 是空字串 display 預設是 "omitted"。要看到摘要得明確寫 thinking={"type": "adaptive", "display": "summarized"}。
    AttributeError on stop_details stop_details 只在 stop_reason == "refusal" 時有值，其他情況是 None。取用前要先判斷。
    Pydantic 報 .dict() 已棄用 Pydantic 2.x 改名了：.dict() → .model_dump()、.json() → .model_dump_json()。
    程式卡住很久才回報錯誤 timeout 會乘上重試次數：最壞是 timeout × (max_retries + 1)。調低其中一個。
