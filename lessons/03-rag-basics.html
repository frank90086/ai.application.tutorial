    RAG 基礎

    這一課結束時，你會有一個「金流串接文件問答」：使用者問技術問題，系統去文件裡找出相關段落，模型根據那些段落回答，而且附上引用。然後把它包成第三個工具，接到第 2 課的機器人上。

    預估時間 10–12 小時 前置 第 1、2 課 產出 文件問答 v1 + 失敗案例筆記 新東西 Docker · pgvector · embedding

    0這一課要做到什麼

    第 2 課的機器人能查交易資料，但查不了知識。使用者問「3D Secure 驗證失敗的錯誤碼有哪些」或「退刷要多久入帳」，這些答案在技術文件裡，不在資料庫的欄位裡。

    直覺的做法是把整份文件塞進 system prompt。但這行不通：

    問題說明
    貴一份 20 萬 token 的文件，每次對話都付一次錢。用 claude-opus-5-5 一次就是 $0.80，問 100 次就是 $80
    慢輸入越長，首個 token 的延遲越高
    品質反而下降大量無關內容會稀釋注意力，模型更容易抓錯重點
    會超過上限文件庫一大就塞不下，而且你無法控制它成長

    RAG（Retrieval-Augmented Generation，檢索增強生成）的做法是：先用程式找出最相關的那幾段，只把那幾段給模型。

    本週產出

    1. 文件問答 v1：能回答金流串接的技術問題，而且附上引用的文件段落。
    2. 一份「檢索失敗案例」筆記：用兩種切塊大小各跑 10 個問題，記下哪些問題檢索失敗、為什麼。

    那份筆記比程式碼更重要——它直接變成第 4 週黃金測試集的內容。第 4 週要量「改動前後 recall@5 從多少到多少」，沒有這份失敗案例清單就沒得量。

    資料來源：只用公開文件

    這是整個八週計畫的硬性限制。本週要收集金流串接文件，只能用公開在網路上的技術文件（例如 Stripe、綠界、藍新這類金流商的公開 API 文件），不要碰公司內部文件、不要用真實的交易紀錄或卡號。

    這不只是合規考量，也是作品集考量——你的 repo 要能公開給招募方看。裡面有一份不能公開的文件，整個專案就不能放上 GitHub。

    1用 Docker 起 Postgres + pgvector

    為什麼是 Postgres 而不是專門的向量資料庫

    市面上有 Pinecone、Weaviate、Qdrant、Chroma 等專門的向量資料庫。這個計畫選 pgvector（Postgres 的擴充套件）的理由是：

    • 你已經會 SQL。向量搜尋變成一個 ORDER BY，不用另學一套查詢語言和一套維運方式。
    • 可以和關聯式資料混用。「找出和這個問題相關、而且 source = '綠界'、而且 version >= 2 的段落」——這在純向量資料庫裡要另外處理，在 Postgres 裡就是 WHERE。
    • 第 4 週要做 hybrid search，需要關鍵字檢索（BM25 / 全文檢索）和向量檢索結合。Postgres 兩個都有。
    • 面試加分。「我用 Postgres + pgvector，因為我們的資料本來就在 Postgres，不想為了向量搜尋多維護一套系統」是一個成熟的工程判斷，比「我用了 Pinecone」更有說服力。

    三個刻意的設定

    • pgvector/pgvector:pg17——這是官方預先裝好 pgvector 擴充的映像。用一般的 postgres 映像的話，你得自己編譯安裝擴充，很麻煩。
    • "5433:5432"——把容器的 5432 對應到你機器的 5433。如果你本機已經裝了 Postgres（很多人有），用 5432 會衝突，而錯誤訊息通常是「連得上但資料庫不存在」這種很難懂的狀況。換個 port 省事。
    • volumes: pgdata——資料存在具名 volume 裡，docker compose down 之後資料還在。沒有這個的話容器一刪資料就沒了，你得重新 embedding（要花錢）。

    檔名用 compose.yaml，不要用 docker-compose.yml

    兩個理由。第一，compose.yaml 是 Docker Compose v2 的官方建議檔名。第二，這個 repo 的 .gitignore 繼承自一個 Visual Studio 模板，裡面有一條 docker-compose.yml——用那個檔名的話，你 git add 會被靜默忽略，沒有任何錯誤訊息。

    1
    啟用 pgvector。每個資料庫只要跑一次，但加 IF NOT EXISTS 讓腳本可以重複執行。
    2
    source：這段來自哪個文件來源（綠界、Stripe…）。之後要用它做 metadata 篩選，所以單獨開一欄而不是埋在內容裡。
    3
    heading：這段所屬的章節標題。這一欄是回答品質的關鍵——切塊會讓段落失去上下文，把標題存下來可以補回來，第 3 節詳述。
    4
    url：原始文件的網址。引用要能點回去，不然使用者無法查證。
    5
    chunk_index：這是文件裡的第幾塊。用來把相鄰的塊接回去，也方便 debug。
    6
    token_count：存下來才能分析「切塊大小的分布對不對」，也能在組 prompt 前估算總長度。
    7
    vector(1024) 是 pgvector 的型別，括號裡是維度，必須和你的 embedding 模型一致。對不上會在插入時直接報錯。pgvector 的一般向量上限是 2000 維。
    8
    給 source 建一般索引，metadata 篩選才快。注意向量索引還沒建——那要等資料載完才建，第 4 節說明原因。

    用 Python 連進去

    uv add "psycopg[binary]" pgvector

    是 psycopg（第 3 版），不是 psycopg2

    Python 的 Postgres 驅動有兩代。psycopg2 是舊版，網路上大多數教學用它；psycopg（沒有數字，版本號是 3.x）是新版，API 比較現代而且支援 async。新專案用 psycopg。

    [binary] 表示裝預先編譯好的版本，不需要本機有 C 編譯器和 Postgres 開發標頭檔——在 Mac 上這會省掉很多麻煩。

    import os
import psycopg
from pgvector.psycopg import register_vector

DSN = os.getenv(
    "DATABASE_URL",
    "postgresql://rag:ragpass@localhost:5433/ragdb",
)


def connect() -> psycopg.Connection:
    """開一個連線，並註冊 vector 型別。"""
    conn = psycopg.connect(DSN)
    register_vector(conn)      # 少了這行，vector 欄位會變成字串
    return conn

    忘記 register_vector(conn) 的症狀

    插入時 psycopg 不知道怎麼把 Python 的 list 轉成 vector，會報型別錯誤；查詢時回來的向量會變成一長串字串而不是數值陣列。這兩種錯誤訊息都不會提到 register_vector，所以先記住它。

    每開一個新連線都要呼叫一次。所以把它包進 connect() 裡，不要散落在各處。

    2Embedding：把文字變成可以比較的數字

    概念

    Embedding 模型把一段文字轉成一串固定長度的數字（向量），例如 1024 個小數。這串數字的特性是：意思相近的文字，向量在空間中的位置也相近。

    "退刷多久會入帳"       → [0.021, -0.183, 0.094, ...]  ┐ 這兩個向量
"退款需要幾個工作天"   → [0.019, -0.177, 0.101, ...]  ┘ 距離很近

"3D Secure 怎麼啟用"   → [-0.144, 0.302, -0.055, ...]   距離遠

    所以「找出和問題相關的段落」就變成一個數學問題：找出向量距離最近的那幾段。這就是為什麼它快——不需要讀過每一段，資料庫用索引就能找。

    第一個重要事實：Anthropic 沒有 embedding 模型

    你的 Anthropic API key 不能拿來做 embedding

    Claude 只有生成模型，Anthropic 官方文件明講「Anthropic does not offer its own embedding model」。所以這一步你需要另一個供應商。

    很多人在這裡卡住，因為前兩課都只用 Anthropic 的 key，會自然以為 embedding 也在同一個 API 裡。

    選哪一個

    選項優點要考慮的
    Voyage AI
    Anthropic 官方推薦    		多語言品質好；有 voyage-finance-2 這個金融領域專用模型；有 rerank 模型（第 4 週要用）要再辦一個帳號和 key
    OpenAI embeddings你第 1 課已經有 key 了，少一個帳號沒有金融領域特化模型
    本機模型（Ollama）免費、無限次實驗、資料完全不出本機品質較差；要自己確認中文支援

    以你的金流背景，這裡有個很好的面試素材

    「哪些資料可以送到外部 embedding API，哪些必須用本機模型」是金融業真實會遇到的問題。建議你兩種都接起來，用同一組測試比較品質差多少——然後你就能具體回答「本機模型在我們的場景下 recall 掉了多少，值不值得為了資料不出境付這個代價」。

    這比空泛地說「我考慮過資料安全」有力得多，也呼應第 7 週的合規主題。

    Voyage 的用法

    uv add voyageai
# 在 .env 加上 VOYAGE_API_KEY=pa-xxxx
    embedding 的呼叫 · 點標記看說明
    import voyageai

vo = voyageai.Client()          # 自動讀 VOYAGE_API_KEY

MODEL = "voyage-4"
DIMENSION = 1024


def embed_documents(texts: list[str]) -> list[list[float]]:
    """把文件段落轉成向量（建立索引時用）。"""
    result = vo.embed(texts, model=MODEL, input_type="document")
    return result.embeddings


def embed_query(text: str) -> list[float]:
    """把使用者的問題轉成向量（檢索時用）。"""
    result = vo.embed([text], model=MODEL, input_type="query")
    return result.embeddings[0]
    1
    和 Anthropic SDK 一樣，不要把 key 寫進程式碼，讓它自己讀環境變數。
    2
    模型名稱和維度寫成常數綁在一起。維度必須和資料表的 vector(1024) 一致，放在一起才不會改了一個忘了另一個。
    3
    vo.embed() 吃一個 list，一次送多段比一段一段送快很多也便宜（少掉每次的網路往返）。建索引時務必批次送。
    4
    查詢時雖然只有一段文字，還是要包成 list，然後取 [0]。這是 API 的形狀。

    input_type：最容易漏掉、而且漏掉不會報錯

    文件用 "document"，問題用 "query"，兩個都不能省

    Voyage 會依照 input_type 在文字前面加上不同的提示句再做 embedding：查詢加的是「Represent the query for retrieving supporting documents:」，文件加的是「Represent the document for retrieval:」。

    這讓問句和文件段落被放到更適合互相比對的向量空間位置。省略或設成 None 會讓檢索品質下降，但程式照跑、沒有任何錯誤訊息——你只會覺得「這個 RAG 怎麼不太準」。

    另一個同類的坑：索引和查詢必須用同一個模型

    不同 embedding 模型產生的向量完全不能互相比較，即使維度剛好一樣。所以：

    • 換 embedding 模型 = 整個資料庫要重新 embedding，不是改個設定就好。
    • 把模型名稱也存進資料表（或至少寫進 README），不然三個月後你會忘記這批向量是用什麼做的。

    這是 RAG 專案最常見的「怎麼突然全部查不到了」的原因。

    3文件準備與切塊

    切塊（chunking）是 RAG 裡最影響品質、而且最沒有標準答案的一步。這一節會解釋各種策略的取捨，但本週實作任務要你親自比較兩種切塊大小——因為最佳值取決於你的文件和你的問題，不是查得到的常數。

    文件來源

    找公開的金流串接技術文件。幾個方向：

    • 國際金流商的公開 API 文件（Stripe 的文件結構清楚、範例多，適合當第一份）
    • 國內金流商公開在官網的技術串接文件（綠界、藍新等都有公開的 API 說明）
    • 卡組織公開的錯誤碼與規範說明

    抓取網頁前先看一下對方的規則

    要大量抓取時，先看 robots.txt 和網站的使用條款，控制請求頻率（加個 time.sleep(1)），別把人家的站打爆。本週的量級很小（幾十頁），手動存成檔案其實也完全可行，而且更快。

    建議：先手動存 20–30 頁就好。這一課的重點是切塊和檢索，不是寫爬蟲。文件數量太少反而會讓你看不出檢索的問題——但 20–30 頁已經夠產生失敗案例了。

    為什麼要切塊

    1. embedding 模型有長度上限（Voyage 4 系列是 32,000 token），整份文件塞不進去。
    2. 更根本的理由：一個向量只能表達一個意思。把一整份 50 頁的文件壓成 1024 個數字，那些數字會是所有主題的「平均」，對任何具體問題都不夠近。
    3. 檢索出來的東西要放進 prompt，太大塊就失去 RAG 省 token 的意義。

    策略一：固定長度切

    def chunk_fixed(text: str, size: int = 500, overlap: int = 80) -> list[str]:
    """固定字數切塊，相鄰塊之間重疊 overlap 個字。"""
    if size <= overlap:
        raise ValueError("size 必須大於 overlap，否則會無限迴圈")

    chunks = []
    start = 0
    while start < len(text):
        end = start + size
        chunks.append(text[start:end])
        start = end - overlap          # 往回退一點，製造重疊
    return chunks

    text[start:end] 是切片（slicing）

    Python 的切片取「從 start 到 end 之前」的子字串，不包含 end。而且切片不會越界報錯——text[0:999999] 在只有 100 個字的字串上會安靜地回傳整個字串。這個特性讓上面的迴圈不需要特別處理最後一塊。

    overlap 是做什麼的

    如果不重疊，一個句子剛好被切在中間時，兩邊都殘缺：

    沒有 overlap：
  塊 1：「…退刷申請送出後，款項會在」
  塊 2：「3 至 7 個工作天內退回原卡…」
  → 問「退刷要多久」時，兩塊都不完整，檢索可能兩塊都不夠相近

有 overlap（重疊 80 字）：
  塊 1：「…退刷申請送出後，款項會在 3 至 7 個工作天內退回原卡…」
  塊 2：「…款項會在 3 至 7 個工作天內退回原卡，若超過期限請…」
  → 完整的句子至少出現在一塊裡

    代價是儲存和 embedding 成本增加（重疊的部分被處理兩次）。常見比例是塊大小的 10–20%。

    策略二：依標題結構切（技術文件建議用這個）

    技術文件通常有清楚的標題層級。依標題切，每一塊天生就是一個完整的主題，比按字數硬切合理得多：

    import re
from dataclasses import dataclass


@dataclass
class Chunk:
    content: str
    heading: str
    chunk_index: int


def chunk_by_heading(markdown: str, max_size: int = 1200) -> list[Chunk]:
    """依 Markdown 標題切塊；單一章節過大時再按段落切開。"""
    # 以 ## 或 ### 開頭的行當分隔點
    parts = re.split(r"\n(?=#{2,3} )", markdown)

    chunks: list[Chunk] = []
    for part in parts:
        part = part.strip()
        if not part:
            continue

        first_line = part.split("\n", 1)[0]
        heading = first_line.lstrip("#").strip() if first_line.startswith("#") else ""

        if len(part) <= max_size:
            chunks.append(Chunk(part, heading, len(chunks)))
            continue

        # 章節太大：按空行分段，累積到接近上限才切
        buf = ""
        for para in part.split("\n\n"):
            if len(buf) + len(para) > max_size and buf:
                chunks.append(Chunk(buf.strip(), heading, len(chunks)))
                buf = ""
            buf += para + "\n\n"
        if buf.strip():
            chunks.append(Chunk(buf.strip(), heading, len(chunks)))

    return chunks

    r"\n(?=#{2,3} )" 這個正規表示式

    • r"..." 是 raw string，裡面的 \n 不會被 Python 先解讀。寫正規表示式一律加 r 前綴。
    • (?=...) 是前瞻斷言（lookahead）：「這個位置後面要符合這個樣式，但不要把它吃掉」。所以切完之後標題還留在後面那一塊的開頭——這正是我們要的。
    • #{2,3} 表示 2 到 3 個 #，也就是 ## 和 ###。不切 #（文件標題）是因為那通常只有一個。

    切塊最大的問題：段落失去上下文

    這是 RAG 品質問題的頭號來源

    看這個被切出來的塊：

    「此欄位為必填，長度上限 20 字元。若未帶入，交易將以錯誤碼 14 退回。」

    這段話在原文裡很清楚，因為上面有標題「MerchantTradeNo（訂單編號）」。但切出來之後，「此欄位」指的是什麼完全不知道了。

    更糟的是：使用者問「訂單編號有什麼限制」時，這一塊的向量裡根本沒有「訂單編號」這個概念，所以檢索撈不到它。這不是模型笨，是你的索引裡就沒有可以匹配的東西。

    最簡單有效的解法：把標題拼回內容再做 embedding。

    def text_for_embedding(chunk: Chunk, doc_title: str) -> str:
    """做 embedding 時用的文字 —— 把上下文補回去。"""
    parts = [doc_title]
    if chunk.heading:
        parts.append(chunk.heading)
    parts.append(chunk.content)
    return "\n\n".join(parts)


# 注意：embedding 用補過上下文的版本，但「存進資料庫、之後給模型看」的
# 是原始 content + 另外存的 heading 欄位。兩者用途不同，不要混在一起。

    進階選項：contextualized chunk embedding

    Voyage 有一組 voyage-context-4 模型，直接產生「帶有完整文件上下文」的塊級向量，不需要你手動拼標題，而且 context length 到 120,000。

    本週建議先用手動拼標題的做法，因為你要先親身體會「失去上下文」這個問題。體會過之後再去試 voyage-context-4，你才知道它解決的是什麼，也才能在第 4 週的對照表裡量出它的效果。

    錯誤碼對照表、參數表    		按字數切會把表頭和資料列拆開，剩下的資料列完全沒意義整張表當一塊，不要切。表格大到放不下時，每一列都帶上表頭再切

    金流文件特別容易踩的一個坑

    金流的 API 文件裡，錯誤碼表格和參數表格佔了很大比例，而這正是按字數硬切最會壞掉的地方。如果你發現「問錯誤碼的問題檢索都很爛」，九成是表格被切壞了。

    4寫入向量庫

    批次寫入

    def ingest(chunks: list[Chunk], source: str, doc_title: str, url: str) -> int:
    """把切好的塊做 embedding 並寫進資料庫。回傳寫入筆數。"""
    texts = [text_for_embedding(c, doc_title) for c in chunks]

    # 分批送 embedding —— 一次全送可能超過 API 的單次上限
    vectors: list[list[float]] = []
    BATCH = 64
    for i in range(0, len(texts), BATCH):
        vectors.extend(embed_documents(texts[i:i + BATCH]))
        print(f"  embedding {min(i + BATCH, len(texts))}/{len(texts)}")

    rows = [
        (source, doc_title, c.heading, url, c.chunk_index,
         c.content, len(c.content), v)
        for c, v in zip(chunks, vectors)
    ]

    with connect() as conn:
        with conn.cursor() as cur:
            cur.executemany(
                """INSERT INTO chunks
                   (source, doc_title, heading, url, chunk_index,
                    content, token_count, embedding)
                   VALUES (%s, %s, %s, %s, %s, %s, %s, %s)""",
                rows,
            )
        conn.commit()

    return len(rows)

    兩個 Python 細節

    • zip(chunks, vectors)：把兩個等長的 list 配對成 (chunk, vector) 的序列。如果長度不一樣，zip 會安靜地在短的那個結束——不會報錯。所以 embedding 如果少回傳幾個，你會靜默少寫幾筆資料。謹慎一點可以先 assert len(chunks) == len(vectors)。
    • range(0, len(texts), BATCH)：第三個參數是步長，所以這會產生 0, 64, 128…，配合切片就是分批。

    另外注意 psycopg 的佔位符是 %s（不是第 2 課 sqlite3 的 ?），但原則完全一樣：永遠不要用字串拼接組 SQL。

    建立向量索引（資料載完之後）

    -- 餘弦距離的 HNSW 索引
CREATE INDEX IF NOT EXISTS chunks_embedding_idx
    ON chunks USING hnsw (embedding vector_cosine_ops);

    三件必須對上的事

    1. 索引要在資料載完之後才建。pgvector 官方明說「像其他索引型別一樣，載入初始資料之後再建索引比較快」。先建索引再灌資料，每一筆插入都要更新索引，慢很多。
    2. 索引的 operator class 必須和你查詢用的距離運算子一致。建了 vector_cosine_ops 的索引，查詢就要用 <=>（餘弦距離）。用成 <->（L2）的話查詢仍然會正確執行，但走不到索引——資料少時你完全看不出來，資料多了之後會突然變很慢。
    3. 維度要對上。vector(1024) 和你的 embedding 模型輸出必須一致。

    距離運算子對照

    運算子距離索引 operator class備註
    <=>餘弦距離vector_cosine_ops文字檢索最常用
    <->L2（歐幾里得）vector_l2_ops
    <#>負內積vector_ip_ops注意是「負」的，所以也是越小越近
    <+>L1（曼哈頓）vector_l1_ops

    Voyage 的向量已經正規化，所以三種距離排序一樣

    Voyage 的 embedding 長度都是 1，這種情況下餘弦相似度和內積相同，而且餘弦距離和歐幾里得距離排出來的順序完全一致。

    所以用哪個都不影響結果，但要和索引的 operator class 對上。本課統一用餘弦（<=> + vector_cosine_ops），因為它是文字檢索的慣例，也不依賴「向量已正規化」這個前提——換成別家的 embedding 模型時比較不會出事。

    HNSW 還是 IVFFlat

    HNSWIVFFlat
    查詢效能較好較差
    建索引速度較慢較快
    記憶體較高較低
    需要訓練階段不需要需要（所以更要先有資料）

    本週用 HNSW。你的資料量很小（幾千塊），建索引的時間差異感覺不出來，而查詢品質比較好。IVFFlat 要到資料量很大、記憶體吃緊時才值得考慮。

    from dataclasses import dataclass


@dataclass
class Hit:
    id: int
    content: str
    heading: str
    doc_title: str
    source: str
    url: str
    distance: float


def search(query: str, k: int = 5, source: str | None = None) -> list[Hit]:
    qv = embed_query(query)

    sql = """
        SELECT id, content, heading, doc_title, source, url,
               embedding <=> %s AS distance
        FROM chunks
        {where}
        ORDER BY embedding <=> %s
        LIMIT %s
    """
    params: list = [qv]
    where = ""
    if source:
        where = "WHERE source = %s"
        params.append(source)
    params.extend([qv, k])

    with connect() as conn:
        rows = conn.execute(sql.format(where=where), params).fetchall()

    return [Hit(*row) for row in rows]
    1
    用 @dataclass 而不是 dict，取值時有自動完成、拼錯欄位名會立刻報錯。這是第 1 課提過的原則：程式內部自己算出來的資料用 dataclass，外部來的才用 Pydantic。
    2
    問題要用 embed_query（input_type="query"），不是 embed_documents。見 §2。
    3
    把距離一起選出來。你需要這個數字來判斷「撈到的東西到底有多相關」——沒有它就無法設相關性門檻，也無法 debug。
    4
    ORDER BY embedding <=> %s 就是整個向量搜尋。注意這裡的運算子要和索引的 operator class 一致，否則走不到索引。
    5
    查詢向量在 SQL 裡出現兩次（SELECT 和 ORDER BY），所以參數也要傳兩次。順序必須和 %s 出現的順序一致。
    6
    metadata 篩選就是普通的 WHERE——這是用 Postgres 的最大好處。「只找綠界的文件」「只找 2024 年之後更新的」都是這樣加。
    7
    這裡用 .format() 組 SQL 只因為 where 是我們自己寫死的字串，不是外部輸入。真正的值一律走參數化（%s）。把使用者輸入 format 進 SQL 就是第 2 課講的 injection 漏洞。

    k 要設多少

    k效果
    太小（1–2）正確答案常常不在裡面。而且模型看不到就答不出來，不管它多聰明
    剛好（3–8）多數情況的起點。本週從 5 開始
    太大（20+）塞進去的無關內容會稀釋注意力、增加成本，而且會讓模型更容易被不相關的段落帶偏

    k 是第 4 週要量的東西，不是現在猜的

    第 4 週的 recall@k 指標就是在回答「k 設多少時，正確答案有多少比例會被撈進來」。本週先固定 k=5 把流程跑通，並把「答案明明在文件裡但沒被撈到」的案例記下來——那些就是第 4 週要改善的目標。

    RAG_SYSTEM = """你是金流技術文件的問答助手，服務對象是客服專員。

## 絕對規則
- 只根據下面提供的「文件片段」回答。不要使用你的既有知識補充。
- 文件片段裡沒有的資訊，直接說「提供的文件中沒有這項資訊」。
- 每一個事實陳述後面都要標註來源編號，格式為 [1]、[2]。
- 可以同時引用多個片段，例如 [1][3]。
- 如果不同片段互相矛盾，指出矛盾並同時引用兩者，不要自己選一個。

## 輸出格式
- 繁體中文，先給結論再給細節。
- 最後不要再列參考資料清單，程式會自己附上。
"""


def build_context(hits: list[Hit]) -> str:
    blocks = []
    for i, h in enumerate(hits, 1):
        header = f"[{i}] 來源：{h.source}／{h.doc_title}"
        if h.heading:
            header += f"／{h.heading}"
        blocks.append(f"{header}\n{h.content}")
    return "\n\n---\n\n".join(blocks)


def answer(question: str, k: int = 5) -> tuple[str, list[Hit]]:
    hits = search(question, k=k)

    if not hits:
        return "找不到相關的文件段落。", []

    user_content = (
        f"## 文件片段\n\n{build_context(hits)}\n\n"
        f"## 問題\n\n{question}"
    )

    response = client.messages.create(
        model="claude-opus-5-5",
        max_tokens=2048,
        system=RAG_SYSTEM,
        output_config={"effort": "low"},
        messages=[{"role": "user", "content": user_content}],
    )

    return text_of(response), hits

    為什麼編號要用 [1] 而不是直接給網址

    • 省 token：網址每次都重複很浪費，而且很長。
    • 好驗證：編號對應到 hits 的索引，你的程式可以檢查模型引用的編號是否存在——引用了 [7] 但你只給了 5 段，那就是幻覺，可以自動抓出來。
    • 好呈現：最後由程式把編號對應回真實的標題和網址，格式統一且一定正確。

    import re


def check_citations(text: str, n_hits: int) -> list[str]:
    """回傳引用相關的問題清單。空 list 表示沒問題。"""
    cited = {int(m) for m in re.findall(r"\[(\d+)\]", text)}
    problems = []

    out_of_range = [c for c in sorted(cited) if c < 1 or c > n_hits]
    if out_of_range:
        problems.append(f"引用了不存在的編號：{out_of_range}")

    if not cited and "沒有這項資訊" not in text:
        problems.append("回答裡完全沒有引用")

    return problems

    這段程式是第 4、6 週的伏筆

    這是你的第一個自動化品質檢查——不需要人、不需要另一個模型，純程式就能抓出一類幻覺。第 4 週會在這個基礎上加 faithfulness（回答有沒有忠於文件）評估，第 6 週會把它變成 CI 裡的回歸測試。

    原則：能用程式檢查的，就不要用 LLM 檢查——便宜、快、而且結果穩定。

    {int(m) for m in ...} 是集合推導式

    大括號 {} 加推導式產生的是 set（集合），會自動去重。這裡用 set 是因為同一個編號被引用好幾次沒關係，我們只在意「用到了哪些編號」。

    如果寫成中括號 [] 就是 list（保留重複），寫成 {k: v for ...} 則是 dict。

    要記錄什麼

    失敗案例筆記的格式

    對每個檢索失敗的問題，記下這四件事：

    1. 問題是什麼
    2. 正確答案在文件的哪裡（哪個章節）
    3. 實際撈到了什麼（前 5 名是哪些段落、距離多少）
    4. 你判斷的原因——表格被切壞？失去上下文？問題用的詞和文件完全不同？是精確字串匹配問題？

    第 4 點最重要。「為什麼失敗」決定了第 4 週要用哪個手段去修：失去上下文 → 改切塊策略；精確字串 → hybrid search；用詞不同 → 查詢改寫或 rerank。沒有分類的話，第 4 週就只能亂試。

    預期你會看到的結果

    通常沒有哪一邊全面獲勝——小塊在精確問題上較好（雜訊少），大塊在需要上下文的問題上較好。這個「沒有最佳解」的體感很重要，它說明了為什麼第 4 週需要用數字來決定，而不是憑感覺挑一個。

    如果你的結果是某一邊全贏，先懷疑是不是問題太簡單了——加幾個更刁鑽的問題進去。

    10自我檢核

    1為什麼不直接把整份文件塞進 context？現在模型不是有 1M context window 嗎？

    技術上塞得下，但四個問題：成本（每次對話都付一次全文的錢）、延遲（輸入越長首 token 越慢）、品質反而下降（大量無關內容稀釋注意力）、不可擴充（文件庫一成長就撐不住）。

    Context window 變大改變的是「單次能處理多少」，不是「該不該每次都塞全部」。RAG 解決的是後者。

    2你的 RAG 回答品質很差。要先懷疑檢索還是先懷疑模型？怎麼判斷？

    先懷疑檢索，而且判斷方法很簡單：把撈到的段落直接印出來看，正確答案在不在裡面。

    如果不在，那是檢索問題，調 prompt 或換模型都救不了——模型看不到答案就不可能答對。如果在裡面但模型沒用好，才是 prompt 或模型的問題。

    這就是為什麼第 4 週整整一週都在量檢索指標（recall@k、MRR），而不是在調模型。

    3一個切出來的塊寫著「此欄位為必填，長度上限 20 字元」。為什麼這會造成檢索失敗？怎麼修？

    「此欄位」指的是什麼，在原文裡靠上方的標題交代，切塊之後那個資訊就消失了。所以這一塊的向量裡根本沒有「訂單編號」這個概念，使用者問「訂單編號有什麼限制」時撈不到它。

    最便宜的解法：做 embedding 時把文件標題和章節標題拼回內容前面。注意是「用來做 embedding 的文字」拼，存進資料庫給模型看的還是原始內容加上獨立的 heading 欄位。

    進階解法是用 contextualized chunk embedding 模型（例如 voyage-context-4），由模型自己處理上下文。

    4你把 embedding 模型從 A 換成 B，兩者都是 1024 維。資料庫要做什麼？

    整個資料庫要重新 embedding。維度一樣只是巧合，不同模型產生的向量空間完全不同，彼此的向量沒有可比性。

    如果你只換了查詢端沒換索引端（或反過來），程式會照跑、不會報錯，但檢索結果會變成隨機的。這是 RAG 專案「怎麼突然全部查不到了」最常見的原因。

    防範方式：把模型名稱和維度寫成綁在一起的常數，並且存進資料表或至少記在 README。

    5input_type 不設會怎樣？

    程式照跑，不報錯，但檢索品質下降。

    Voyage 會依 input_type 在文字前加上不同的提示句（query 版和 document 版不同），讓問句和文件段落被對應到更適合互相比對的位置。省略它等於放棄這個優化。

    這類「不會報錯但默默變差」的坑是 RAG 最難 debug 的部分——所以才需要第 4 週的量化評估，靠感覺是察覺不到的。

    6為什麼向量索引要在資料載完之後才建？建錯 operator class 會怎樣？

    先載資料再建索引比較快——先建索引的話，每一筆插入都要更新索引結構。pgvector 官方文件明確建議這個順序。

    operator class 和查詢運算子不一致（例如索引建 vector_cosine_ops 但查詢用 <->）時，查詢仍然會回傳正確結果，但走不到索引，變成全表掃描。資料少時完全看不出來，資料一多就突然很慢——而且因為結果是對的，很難聯想到是索引問題。

    11常見錯誤排查

    症狀原因與解法
    連不上資料庫 / connection refused容器沒起來或還沒 healthy。docker compose ps 看狀態，docker compose logs db 看錯誤。
    連得上但資料表不存在很可能連到本機原本就有的 Postgres（5432）而不是容器。確認 DSN 的 port 是 5433。
    type "vector" does not exist沒跑 CREATE EXTENSION vector;，或跑在別的資料庫上。
    插入向量時型別錯誤忘記 register_vector(conn)。每個新連線都要呼叫。見 §1。
    查詢回來的 embedding 是一長串字串同上，register_vector 沒呼叫。
    expected 1024 dimensions, not 1536embedding 模型的維度和 vector(N) 不一致。改資料表或改模型維度參數。
    檢索結果看起來像隨機的最可能是索引和查詢用了不同的 embedding 模型，或 input_type 用反了。
    檢索品質普通但說不上哪裡錯檢查 input_type 有沒有設。這個不會報錯但會明顯影響品質。
    問錯誤碼的問題都查不到精確字串是向量檢索的弱項，加上表格可能被切壞。記進失敗案例筆記，第 4 週用 hybrid search 解。
    問參數欄位的問題都查不到典型的「失去上下文」。把標題拼回內容再 embedding。見 §3。
    模型編造文件裡沒有的內容system prompt 的「絕對規則」不夠強硬，或 k 太大塞了太多無關段落。先檢查撈到的段落品質。
    模型引用了不存在的編號用 check_citations 抓出來。通常是 k 和實際回傳數量不一致，或 prompt 裡的編號格式不夠明確。
    資料量大了之後查詢變很慢索引的 operator class 和查詢運算子不一致，走不到索引。見 §4。
    docker compose down -v 之後資料沒了-v 會刪 volume。要重新 ingest（會再花一次 embedding 的錢）。平常用不加 -v 的 down。
