    這週不學新東西。七週的成果如果沒人看得懂，就等於不存在——這一課要把它包裝成招募方五分鐘內能理解、而且會想找你聊聊的樣子。

    預估時間 10–12 小時 前置 第 1–7 課 產出 作品集 + 新版履歷 新技術 零

    0這一課要做到什麼

    這週的心態要換一個：前七週你在解決技術問題，這週你在解決溝通問題。

    招募方看你的 repo 大約 2 到 5 分鐘

    他們不會 clone 下來跑、不會讀你的 agent/nodes.py。他們會：看 README 前半頁、看有沒有 demo 連結、掃一下架構圖、看有沒有數字、然後決定要不要往下看。

    你七週的工作，命運取決於 README 的前 30 行。這不公平，但這是事實，而且你可以為此優化。

    本週產出

    1. README——一句話問題陳述、架構圖、評估數字、成本、已知限制。
    2. 3 分鐘 demo 影片——正常流程、人工核准、擋下 injection。
    3. 一篇技術文章——展示你的思考過程，不只是成果。
    4. 新版履歷——把金流經驗重新框架成 AI 應用的優勢。
    5. 面試題準備——五個核心問題，用你自己的專案回答。

## 它解決什麼問題

金流客服每天要在後台查交易、對照錯誤碼、翻串接文件，再手動擬回覆。
這個系統把這三件事串起來，讓客服用一句話就拿到有依據的草稿。

## 安全與合規

- 10 種注入手法的紅隊測試，全部納入回歸測試
- PII 遮罩層（卡號 Luhn 檢查）在資料入口執行
- 退款金額分級 + 人工核准 + 稽核日誌
- [金管會 AI 指引六大原則對照](docs/compliance.md)

## 已知限制

- 使用公開文件與自行產生的假資料，未接任何真實金流系統
- multi_hop 類問題的檢索命中率僅 0.50，尚未解決
- 未做正式的演算法偏誤檢測

## 技術選型與取捨

| 選擇 | 理由 |
|---|---|
| Postgres + pgvector | 資料本來就在 Postgres，不想為向量搜尋多維護一套系統 |
| 手寫 tool 迴圈 → LangGraph | 需要中斷恢復與人工核准，自己實作成本高於框架學習成本 |
| 自架 Langfuse | 資料留在本機，符合金融場景的資料治理考量 |

    6
    安全與合規這一段，一般作品集不會有。對金融業徵才方來說，這是最能把你和其他候選人區分開的部分。
    7
    「已知限制」是整份 README 最反直覺、但最能加分的一節。詳見下方。
    8
    寫「取捨」而不是「技術棧」。列出用了什麼套件誰都會；說得出為什麼選它、放棄了什麼，才是工程判斷。

    為什麼「已知限制」反而加分

    一個沒有限制的系統，只代表作者沒去找

    資深工程師看到一份「什麼都好、什麼都解決了」的 README，第一反應不是佩服，是「這個人還沒踩夠坑」。

    反過來，「multi_hop 類問題的檢索命中率僅 0.50，尚未解決」這句話傳達了三件事：

    1. 你有量到分類別的數據（代表評估做得細）
    2. 你知道自己的系統哪裡弱（代表你真的在用它）
    3. 你誠實（代表你的其他數字也可信）

    第 3 點最重要：誠實的限制說明，會讓你所有其他的宣稱變得可信。

    數字怎麼放

    三分鐘腳本

    時間內容要傳達什麼
    0:00–0:20一句話說明這是什麼、給誰用讓人知道在看什麼
    0:20–1:10正常流程：問「A99001 為什麼失敗，文件建議怎麼處理」，展示它查交易 → 查錯誤碼 → 查文件 → 擬回覆，回答帶引用核心價值。多工具串接是重點
    1:10–2:00人工核准：要求退款，系統停下來顯示核准畫面；示範關掉程式、重開、接續這是最有記憶點的部分
    2:00–2:40擋下 injection：示範一個直接注入被拒絕，再示範知識庫裡藏指令的文件被識破差異化。多數作品集沒有這段
    2:40–3:00快速帶過 Langfuse trace 與 CI 畫面，說一句「每個決定都留得出軌跡」收尾，暗示工程成熟度

    1:10–2:00 這段是整支影片的賣點

    「AI 會停下來等人核准，而且可以關機隔天再繼續」——這個畫面在金融業徵才方眼中的份量，遠超過你的 RAG 準確率。它直接回答了他們心裡最大的疑慮：「這東西會不會自己亂做事」。

    所以這 50 秒要拍清楚，不要急。

    錄製要點

    • 先寫逐字稿再錄。即興講會超時、會跳來跳去。
    • 字體調大。對方可能在手機上看。終端機和瀏覽器都放大到不自然的程度剛剛好。
    • 剪掉等待時間。LLM 回應要幾秒，剪掉或加速。沒人想看載入動畫。
    • 不要用真實個資，連示範用的假卡號都用公開的測試卡號。
    • 三分鐘是上限不是目標。兩分半講完更好。

    3技術文章

    選題：寫「過程」不要寫「教學」

    不要寫「如何用 LangGraph 建立 AI Agent」

    這種文章網路上有幾百篇，而且它展示的是「我會照著文件做」，不是你的判斷力。招募方看了也記不住你。

    選題方向例子為什麼有效
    量化的前後對照「我的 RAG 檢索命中率從 0.62 到 0.89：三個改動與它們各自的效果」有數據、有方法，別人複製不了你的數字
    踩坑實錄「做金流文件 RAG 踩到的五個坑：表格被切壞、中文斷詞、以及 Postgres 全文檢索的限制」具體、有領域特性、幫到人
    領域交叉「金流背景的人做 AI agent：我怎麼設計退款的人工核准與稽核軌跡」只有你寫得出來
    評估方法「金流客服 agent 的 evals 怎麼做：從 30 題測試集到 CI 回歸測試」多數人做不好評估，這題稀缺

    第三個方向是你的最佳選擇

    「金流背景 + AI agent 的安全與合規設計」這個交叉，市面上幾乎沒人寫——因為會 AI 的通常不懂金流的細節（錯誤碼、對帳、退款風險、冪等鍵），懂金流的通常不做 AI。

    你同時有兩邊，這是你最大的不可替代性。文章就該寫在這個交叉點上。

    4履歷改寫

    把金流經驗重新框架

    最常見的錯誤：把金流經驗當成「要被取代掉的過去」

    很多轉職的人會把舊經驗壓縮成一行，急著證明自己「現在是做 AI 的」。這是在丟掉你最大的優勢。

    AI 應用工程師的職缺有很多人投，多數是純軟體背景。你的差異化不是「我也會 RAG」，而是「我會 RAG，而且我知道金融系統的可靠性與合規要求長什麼樣」。

    原本的寫法重新框架
    負責金流系統串接與維運負責高可靠性金流系統，熟悉冪等設計、對帳機制與交易異常處理——這些正是 AI agent 執行高風險動作時需要的保證
    處理交易爭議與退款流程熟悉退款風險控制與稽核要求，據此設計 AI agent 的分級核准機制與決策軌跡保存
    配合法遵需求調整系統具備金融法遵脈絡，能將金管會 AI 指引轉譯為具體的工程控制措施
    處理客戶個資相關作業熟悉個資處理規範，實作 PII 遮罩層確保敏感資料不進入外部 LLM API

    每一條都用「金流經驗 → 所以我在 AI 系統上做了什麼」的句型

    這個句型的威力在於：它把你的過去變成現在的理由，而不是需要被原諒的背景。

    而且每一條都指得到你 repo 裡的實際程式碼——面試時可以直接打開給對方看。

    5面試題準備

    以下五題是計畫明確列出的，而且你前七週的每一課都剛好準備了素材。這裡給的是答題框架與你可以引用的具體內容。

    1RAG 常見的失敗原因有哪些？

    先給框架：失敗可以分在三個階段。

    • 切塊階段：失去上下文（「此欄位」不知道指什麼）、表格被切壞、程式碼區塊和說明被拆開。
    • 檢索階段：精確字串（錯誤碼、欄位名）向量檢索不可靠；使用者用詞和文件差太遠；答案跨多個段落。
    • 生成階段：撈到了但模型沒用、或是加了文件裡沒有的東西。

    然後給你的實例：「我的測試集裡 exact_string 類在純向量下只有 0.30，加了 hybrid search 之後到 0.88。而 multi_hop 類三種手段都沒改善，停在 0.50——那是切塊策略的問題，不是檢索的問題。」

    最後加一句判斷：「所以我的經驗是，RAG 出問題時要先確認檢索有沒有撈到，再去懷疑模型——否則會一直在調 prompt 但問題根本不在那裡。」（W3）（W4）

    2如何降低幻覺？

    分層回答，從最硬的手段講起：

    1. 結構約束：用 schema 約束輸出（structured output），讓不合法的格式在生成階段就不可能發生。
    2. 限定依據：RAG 加上「只根據提供的片段回答」與強制引用編號。
    3. 程式驗證：引用編號存不存在、回答裡的數字有沒有出現在來源段落裡——這些用正規表示式就能查，不用 LLM。
    4. 量測：faithfulness judge，而且要人工校準過才可信。
    5. 設計層：負面案例（文件裡沒答案）要進測試集，否則一個「永遠生出答案」的系統會拿滿分。

    關鍵的一句：「在金流場景，『不知道就說不知道』是功能不是缺陷——客服拿瞎掰的答案去回覆消費者，比多查一次嚴重得多。」（W4）

    3有哪些成本優化手段？

    照「免費的先做、有代價的後做」排序：

    • Prompt caching（免費，只要前綴穩定）——工具迴圈多輪時效果最明顯。注意任何會變的東西都要移到標記點之後。
    • 輸出比輸入貴約 5 倍——所以「讓模型少講話」的效益遠大於「讓它少讀東西」。用 enum、限制輸出長度、分類任務的 max_tokens 設小。
    • 降低 effort——比換模型更該先試的一步。
    • 混合模型——輸出空間受限的節點（意圖判斷、judge）用便宜模型。但要注意 cache 是綁模型的。
    • 減少不必要的步數——agent 繞路就是在燒錢，要有可觀測性才看得到。

    給實例：「我量過三種配置，全 opus 和生成用 sonnet 的情境通過率相同（19/20，而且失敗的是同一題），但成本差 2.3 倍，所以我選了後者並寫下決策紀錄。」（W6）

    4什麼時候不該用 agent？

    先表態：「能寫死的步驟就寫死——每個『讓模型決定』的環節都是一個不確定性來源，更難測、更難 debug、更貴。」

    給判準（四個都要成立才值得）：複雜度（多步驟且無法事先規定）、價值（值得更高成本與延遲）、可行性（模型做得到）、錯誤成本（錯了能被發現並補救）。

    關鍵洞察：「而且要逐個動作判斷，不是整個流程一起決定。我的系統裡擬回覆交給模型，因為錯了有人會看到；但執行退款不行，因為錢出去回不來——所以那一步是固定流程加人工關卡。」

    加一句架構層面的：「我兩種都實作過同一個流程。分界線是『需不需要暫停與恢復』——不需要的話手寫迴圈更簡單、相依更少。」（W5）

    5怎麼評估一個 LLM 功能？

    這題是你最該答好的一題，因為多數候選人答不好。

    1. 先有測試集：問題 + 應命中段落 + 標準答案 + 分類。分類最重要——總分會上下跳動但看不出所以然，分類別才指得出下一步。
    2. 必須有負面案例：否則「永遠生出答案」的系統拿滿分。
    3. 評分方法由便宜到貴：程式檢查 → 成對比較 → 單點 rubric → 人工。能用程式查的就不要用 LLM。
    4. judge 用二元判定不用 1–5 分：模型對「3 分和 4 分的差別」沒有穩定標準，而且二元判定強迫你把「什麼情況算 fail」寫清楚——那個動作本身就是評估最有價值的部分。
    5. judge 必須人工校準：抽 10 題自己先判再比對一致率，低於 9/10 就改判定條件。沒校準過的 judge 給的數字沒有意義。
    6. 要能一個指令重跑，並進 CI。

    收尾：「評估做好之後最大的改變是——我敢動大刀了。第 5 週我把整個架構從手寫迴圈換成 LangGraph，換完跑一次 eval 就知道有沒有退步。」（W4）（W6）

    6（高機率追問）你怎麼處理 prompt injection？

    先講清楚它的本質：「對 LLM 來說 context 裡所有文字都是 token，它沒有機制區分『可信指令』和『待處理資料』。所以目前沒有能根除它的方法，只能分層降低風險。」

    講分層，而且強調最有效的一層不在 prompt：「架構層——高風險動作一律人工核准。注入可以騙過模型，但騙不過要按核准鍵的人。接著是權限層、輸入框界、提示層、輸出遮罩、偵測告警。」

    一句能展現功力的話：「我會區分 prompt 和程式控制——prompt 是降低機率，程式是消除可能。在 system prompt 裡寫『不要洩漏卡號』有幫助但不是安全控制；讓卡號根本不進入 context 才是。」

    給實例：「我做了 10 種手法的紅隊測試，包含在知識庫裡塞一份含惡意指令的文件、在交易備註欄塞指令——間接注入光在輸入框打字測不出來。全部納入回歸測試了。」（W7）

    面試前把這六題各講一次，計時

    每題控制在 90 秒到 2 分鐘。太短顯得沒深度，太長對方會失焦。

    講的時候用「框架 → 我的實例 → 一句判斷」的結構。「我的實例」那段是別人抄不走的，一定要有。

    6投履歷與回饋循環

    計畫建議在 104、CakeResume、LinkedIn、iPAS 人才媒合平台各投 3–5 個「AI 應用工程師」職缺。重點不是數量，是建立回饋循環。

    不要一次投 50 個

    一次投太多的問題是：如果你的履歷有問題，你會在收到第一個回饋之前就把機會用完了。

    建議節奏：先投 10–15 個 → 看回覆率 → 調整履歷或作品集 → 再投下一批。把它當成第 4 課的 hill climbing，只是這次的 eval 是面試邀約率。

    訊號可能的問題調整方向
    投了 15 個，零面試邀約履歷沒過篩選關鍵字對應、成果句改成有數字的、確認 repo 連結放在顯眼處
    有邀約，但第一關就掛自我介紹沒講清楚差異化練「金流 + AI 安全」這條故事線，不要只講技術
    技術面被問倒深度不足或講不出所以然回頭看是哪一週的內容，補強那一塊
    對方覺得「只有個人專案」缺乏規模感強調你的金流工作經驗，以及專案的工程化程度（CI、evals、可觀測性）
    進到最後但沒上通常不是技術問題禮貌地詢問回饋，這個階段的回饋最有價值

    每次面試後當天寫下被問到的問題

    這份清單會比任何面試題整理都準，因為它是你應徵的那類職缺真正會問的。

    被問倒的題目，回頭看對應的那一課、把答案補起來、如果需要就補做一點實作。這就是計畫裡說的「從面試反饋回頭補強」。

    8常見錯誤

    錯誤為什麼不好 / 怎麼改
    README 開頭先列技術棧對方還不知道這是什麼就看到一串名詞。先講問題，技術選型放後面並附理由。
    架構圖是手畫的且已過時用第 5 課 draw_mermaid() 自動產生的，永遠和程式碼一致。
    數字沒有量測方法「準確率 90%」無法驗證。補上測試集大小與指標定義。
    沒有「已知限制」資深工程師會覺得你還沒踩夠坑。誠實反而加分。
    demo 影片超過 5 分鐘沒人看完。寫逐字稿、剪掉等待、三分鐘是上限。
    影片字太小對方可能在手機上看。放大到不自然的程度剛好。
    文章寫成「如何用 X 建立 Y」網路上幾百篇，展示不出判斷力。寫你的過程與數字。
    履歷把金流經驗壓成一行丟掉最大的差異化。用「金流經驗 → 所以我做了什麼」重新框架。
    關鍵字條列堆砌人看了跳過。放進有數字的成果句裡。
    一次投 50 個職缺收到第一個回饋前就把機會用完。分批投、依回饋調整。
    repo 是 private 卻放進履歷最可惜的失分。用無痕視窗確認過。
    git 歷史裡有舊的 API key當前檔案乾淨不代表歷史乾淨。全歷史搜尋一次。
    CI 徽章是紅的比沒有徽章更糟——它證明你知道壞了但沒修。

    9八週回顧

    回頭看一次你做了什麼。這份清單就是你面試時的素材庫。

    週你學到的能力可以講的實例
    W1LLM API、structured output、成本與延遲量測三模型比較表；為什麼 schema 約束比在 prompt 裡拜託可靠
    W2手寫 tool-use 迴圈、prompt 工程、MCP模型不會執行任何東西，權限控制在你這側；工具 description 比 system prompt 更能改變行為
    W3RAG、pgvector、切塊策略切塊造成的「失去上下文」；RAG 品質上限由檢索決定
    W4黃金測試集、檢索指標、hybrid search、LLM judgeexact_string 類 0.30 → 0.88；為什麼 judge 要人工校準
    W5LangGraph、human-in-the-loop、checkpoint能寫死的就寫死；中斷恢復；手寫迴圈 vs 框架的分界線
    W6Tracing、端到端情境、CI 回歸測試用數據決定換模型的紀錄；為什麼測行為不測文字
    W7紅隊測試、PII 遮罩、權限最小化、部署、合規間接注入實測；prompt 是降低機率、程式是消除可能
    W8把以上全部講清楚——

    八週之後最該記住的三件事

    1. 沒有量測就沒有工程。前三週你靠感覺，第四週開始靠數字——而那是整個計畫的轉折點。所有「我覺得變好了」都該被換成「這個指標從 X 到 Y」。
    2. 把錯誤當成資料，不是例外。工具失敗回 is_error、節點失敗寫進 state、驗證失敗餵回模型——這個模式在第 2、4、5 課各出現一次，它是 LLM 應用的通則。
    3. 模型是不可信的輸入來源。它的輸出要驗證、它的參數要檢查、它的決定在高風險處要有人把關。這不是對模型沒信心，是系統設計的基本紀律——而你的金流背景讓你比多數人更早就懂這件事。

    如果你跑的是 4 週衝刺版

    衝刺版先省略了標記為「加分」的項目。建議一邊投履歷、一邊花 2–3 週補上——特別是這幾項，它們在面試時最常被追問：

    • MCP server（W2）——「你怎麼讓別的系統用你的工具」
    • Hybrid search 與 rerank（W4）——「精確字串查不到怎麼辦」
    • Checkpoint 中斷恢復（W5）——demo 影片最有記憶點的那一段
    • CI 回歸測試（W6）——「你怎麼確定改動沒有弄壞東西」

    然後呢

    這個專案不該在第 8 週凍結。有了 evals 和 CI，它是一個可以持續改進的系統——而「我持續在改進它，這是最近三個月的變化」比「我八週前做了這個」有力得多。

    幾個自然的下一步：那個卡在 0.50 的 multi_hop 類、多輪對話的記憶設計、把 agent 接上更多工具、或是換一個領域驗證你的架構可不可以搬。
